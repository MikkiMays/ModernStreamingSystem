## 2. R210 — аналитика продукта

### 2.1. Что сегодня уже есть и чего не хватает

Есть (E10-B): строка на встречу (`meeting_stats`: длительность, пик людей, человеко-секунды, интеграции, качество),
итоги дня (`activity_daily`), входы и отказы (`audit_events`, 3 месяца), уникальные устройства за сутки (HyperLogLog в
Redis — только число). Этого хватает на «сколько встреч и часов», но **не** на вопросы владельца: кто новый, кто
вернулся, какая доля посетителей дошла до звонка, с какого клиента, когорты. Для них нужна строка на *посетителя*, а
не на встречу, — и первый контакт раньше встречи: открытие сайта.

### 2.2. Модель событий

| Событие | Откуда | Что меняет |
| --- | --- | --- |
| `visit` — открыл сайт/приложение | клиент, `POST /api/v1/visit {stage:"open"}` один раз на сессию вкладки/запуска приложения | `visitor_days.visits += 1`; первая строка `visitors` → «новый посетитель» |
| `prejoin` — дошёл до предвхода (выбор камеры/микрофона) | клиент, то же, `{stage:"prejoin"}` один раз на сессию | `visitor_days.prejoins += 1` |
| `create` / `join` — создал встречу / вошёл | ядро, `Entries.admit` (пять дверей: create, link, code, rejoin, saved) | `creates`/`joins += 1`; первый — `visitors.first_called_at` → «новый звонивший»; отказ — `join_failures += 1` |
| `presence` — на связи | ядро, `RoomObserver.changed/closed`: отрезки `CONNECTED` каждого человека с профилем | `presence_seconds += …` |
| `integration` — открыл интеграцию | ядро, `RoomObserver.changed`: интеграция появилась во встрече → засчитывается ведущему… нет: тому, кто её открыл, ядро не знает без разбора команд, поэтому **встрече** (`meeting_stats.integrations`, как раньше) и каждому, кто был на связи в тот момент (`visitor_days.integrations += 1`) | использование интеграций в обоих измерениях |
| `error` — человек увидел ошибку | ядро, `POST /api/v1/client-errors` (R180) | `visitor_days.errors += сумма сводки` |
| `client` — тип клиента и ОС | заголовок `X-Cord-Client` (web, desktop, android, telegram) + ОС из `User-Agent` словом из перечисления (windows, macos, linux, android, ios, other) | `visitor_days.client/os`, `visitors.first_client/first_os` |

`rejoin` (вернулся в ту же встречу после обрыва) входом не считается — иначе плохая связь выглядела бы ростом звонков.

### 2.3. Личность посетителя и приватность (Р-121)

Учётных записей нет. Личность — профиль устройства: случайный секрет в браузере, ядро знает его `SHA-256`
(`profileHash`, `access/Identity.java`). Он лучше адреса, о котором спросил владелец («с нового айпи получается или
как»): адрес меняется у одного человека (мобильная сеть, VPN) и един для офиса за NAT, профиль — один на устройство.

**Ключ посетителя** `visitor_key = HMAC_SHA256(секрет сервера, "analytics:" + profileHash)`. Второй слой HMAC нужен,
чтобы таблицы аналитики нельзя было соединить с `favorites` или `audit_events` по хэшу профиля, не зная секрета
сервера. Ключ стабилен — иначе невозможны ни «вернулся через 7 дней», ни когорта ЛТВ: дневная соль (как у счётчика
устройств E10-B) эти вопросы делает неотвечаемыми по построению. Компромисс записан явно:

- ключ выводится из случайного секрета устройства, а не из человека; ни адрес, ни имя, ни встречи в таблицах
  аналитики не лежат — только счётчики за день;
- срок — `stream.retention.analytics` (`ANALYTICS_RETENTION`, по умолчанию 400 дней): посетитель, не появлявшийся
  400 дней, забывается целиком;
- наружу (в API, в пульт) ключ не выходит никогда — только агрегаты; очистить всё — `DELETE` двух таблиц;
- **без профиля** (старый клиент, `curl`) посетитель считается по **суточно-солёному** отпечатку адреса
  (`HMAC(секрет, "analytics-day:" + день + ":" + ключ адреса)`): он виден как посетитель этого дня, но между днями
  не склеивается и в когорты/удержание не входит (`visitors.anonymous = true`, строка живёт один день + срок).
  Так адресный след не копится — П8.

Данные остаются в базе продукта на meet; на A не копируются.

### 2.4. Хранение (V16)

```sql
visitors(visitor_key PK, first_seen_at, first_day, first_client, first_os, first_called_at, last_seen_at, anonymous,
         expires_at)
visitor_days(day_utc, visitor_key, client, os, visits, prejoins, creates, joins, join_failures, presence_seconds,
             integrations, errors, expires_at; PK (day_utc, visitor_key))
```

Запись — `INSERT … ON CONFLICT DO UPDATE` (и в PostgreSQL, и в H2 тестов работает `MERGE`-совместимый синтаксис
через `JdbcClient`; см. `Analytics.java`). Присутствие пишется при смене состава «на связи» и при закрытии встречи, как
человеко-секунды в `MeetingStats`: в памяти — только «с какого момента этот участник на связи», перезапуск ядра
теряет лишь текущие незакрытые отрезки.

### 2.5. Два измерения: ЛТВ и АКТУАЛ (Р-122)

Период `[from, to)` по дням UTC (пульт пересчитывает выбранные даты смотрящего; дни в графиках — по его поясу).

- **АКТУАЛ** — всё, что произошло в периоде, кем бы ни было сделано: все строки `visitor_days` с `day_utc` в периоде,
  все встречи `meeting_stats` с `started_at` в периоде. Посетитель, пришедший год назад, здесь считается.
- **ЛТВ** — когорта: посетители, у которых `visitors.first_day` в периоде («кто только в этом периоде пришли»), и
  **вся их активность с первого дня до сегодня** — в периоде и после него. Это и есть «lifetime value»: что принесла
  когорта. Поэтому у ЛТВ есть величины «на посетителя»: часов на связи, входов, интеграций; «встреч» в ЛТВ нет
  (встреча не принадлежит одному человеку), есть «входов во встречи».

Одни и те же плитки в обоих режимах; где величина не имеет смысла в режиме, плитка показывает «—» с подсказкой.

### 2.6. Метрики и их определения (Р-123)

| Метрика | АКТУАЛ | ЛТВ |
| --- | --- | --- |
| Посетителей | различных `visitor_key` с любой строкой дня в периоде | размер когорты |
| Новых посетителей | `first_day` в периоде | = посетителей |
| Вернувшихся | посетителей с `first_day` до периода | — |
| Звонивших | посетителей с `creates+joins > 0` в периоде | когорта с `first_called_at IS NOT NULL` |
| Новых звонивших | `first_called_at` в периоде | то же |
| **ER** (engagement rate) | звонивших / посетителей | звонивших когорты / когорта |
| **Stickiness** (DAU/MAU) | среднее за день число активных / различных активных за период | — |
| Встреч | строки `meeting_stats` в периоде | — |
| Входов во встречи | `SUM(creates+joins)` | то же по когорте |
| Часов на связи | `SUM(presence_seconds)/3600` (и рядом человеко-часы `meeting_stats` — сверка) | то же по когорте + «на звонившего» |
| Средняя и медианная длительность встречи, самая долгая | из `meeting_stats` | — |
| Пик одновременных встреч и людей | развёртка интервалов `meeting_stats` (встречи), `MAX(peak_humans)` | — |
| Воронка | открыли → предвход → вошли (посетителей на шаге); отказы входа | то же по когорте |
| Тип клиента / ОС | посетителей по `client` и `os` строки дня (посетитель на нескольких — в каждом) | по `first_client`/`first_os` |
| Интеграции | встреч с интеграцией (`meeting_stats.integrations`), открытий на посетителя | открытий когорты |
| Ошибок на сессию | `SUM(errors)/SUM(visits)` | то же по когорте |
| Удержание D1/D3/D7/D30 | таблица когорт по неделе первого визита внутри периода | то же, но когорта — весь период |
| По дням | посетители, новые, звонившие, часы — ряд на график | активность когорты по дням от её первого дня |

**Удержание — «вернулся в течение N дней»**: доля когорты, у которой есть строка дня с `first_day < day_utc ≤
first_day + N`. Не «ровно в день N» (у продукта для встреч недельный ритм, строгий D3 был бы нулём) — поэтому
D1 ≤ D3 ≤ D7 ≤ D30 и колонки читаются слева направо. Когорты моложе N дней помечены «ещё рано».

### 2.7. API

```
POST /api/v1/visit               {stage: "open"|"prejoin"}   → 204   (открыт до пароля сервера, предел на адрес,
                                                                       нужен X-Cord-Profile; без него — только счёт дня)
GET  /api/v1/admin/analytics?from&to&mode=actual|ltv&tz=мин  → Analytics (ниже); X-Cord-Admin
```

Ответ — один JSON: `mode`, `from`, `to`, `visitors{total,new,returning,callers,newCallers}`, `rates{er,stickiness,
errorsPerVisit}`, `calls{meetings,entries,presenceHours,meetingHours,avgMinutes,medianMinutes,longestMinutes,
peakMeetings,peakHumans,joinFailures}`, `funnel{opened,prejoined,joined}`, `clients[]`, `os[]`, `integrations[]`,
`days[]`, `retention{cohorts[]}`. Все числа; ключей посетителей нет.

Пульт: `GET /api/fleet/core/{machine}/analytics?…` — чтение, как `meetings`.

### 2.8. Экран «Аналитика»

Период (быстрые кнопки 7/30/90 дней и даты) · переключатель **ЛТВ / АКТУАЛ** (`Segmented`) · плитки · графики (свои
SVG на токенах `ui/kit`: столбики по дням, воронка, разбивка по клиентам) · таблица когорт удержания с заливкой по
доле. Все подписи — `i18n/admin/ru.ts`, определения метрик — подсказками у плиток.

### 2.9. Клиент

`X-Cord-Client` — новый заголовок во всех запросах веба (`web/src/api/client.ts`): `telegram` в Mini App, `desktop` в
оболочке Electron/WebView, `android` в приложении, иначе `web`. Описан в `contracts/headers.md`. Событие `visit`
шлёт `web/src/core/analytics.ts` один раз на сессию вкладки (`sessionStorage`), `prejoin` — при первом показе предвхода.
Обе отправки — `keepalive`, ошибки глотаются: аналитика не должна мешать входу.

## 3. R209 — «Флот — live»

### 3.1. Источники

Всё — из VictoriaMetrics на A (`FLEET_METRICS_URL`), **групповыми запросами на весь флот** (один запрос на величину,
не на машину): `Metrics.live()` в `services/fleet/fleet/metrics.py`. Строки ответа раскладываются по машинам по
меткам: у A ряды подписаны `job="node|cadvisor|core|livekit"`, у машин по туннелям — `machine="fra"` + `kind="node|
containers|core|gateway"` (`infra/generated/scrape-nodes/fleet-*.json`), у узлов по магистрали — `node="hel"` +
`role=`. Что показываем по машине:

| Группа | Ряды |
| --- | --- |
| Железо | ядер (`count(node_cpu_seconds_total{mode="idle"})`), ОЗУ всего, диск всего/свободно, ядро ОС и дистрибутив (`node_uname_info`, `node_os_info`), аптайм (`node_boot_time_seconds`) |
| Нагрузка | ЦП, steal, load1/ядро, память, своп, диск, сеть вход/выход Мбит/с, пакеты, ошибки/дропы, давление PSI (`node_pressure_*`), давление памяти |
| Контейнеры | топ по ЦП и по сети (`container_*{name!=""}`) — **сейчас cAdvisor на fra/msk/hel отдаёт только корневую cgroup** (`id="/"`), и список пуст; плашка так и говорит. Чинится в агенте метрик (главная сессия, `infra/fleet`) |
| Ядро | встреч live/waiting, людей на связи, ботов, экранов, интеграций по видам (`cord_*_active`), входов и отказов в минуту (`rate(cord_joins_total)`), ошибок клиентов в минуту, узлы ядра (`cord_node_rooms`, `cord_node_participants`, `cord_node_up`) |
| SFU | комнаты и участники LiveKit, битрейт вход/выход (`rate(livekit_packet_bytes)`), потери (`livekit_packet_loss_percent`), RTT, качество |
| Кто грузит сеть | встречи из `GET /api/v1/admin/now` ядра машины, упорядоченные по «экранов, людей» — битрейт на встречу SFU не отдаёт, а метка с номером комнаты в метриках запрещена (П8, §4 `observability.md`); оценка — экраны × ~2,5 Мбит/с + люди × ~0,6 Мбит/с, так и подписано |

### 3.2. Экран

Карточка на машину (A, meet, cordcam, B): шапка (имя, роль, аптайм, ОС, ядра/ОЗУ/диск), ряд индикаторов с полосами
(ЦП, steal, ОЗУ, диск, вход/выход), мини-таблицы «Контейнеры», «Ядро», «SFU», «Встречи сейчас». Сверху — сводка флота:
встреч, людей, экранов, интеграций, суммарный исходящий трафик, самая загруженная машина. Обновление раз в 5 с
(`refetchInterval`), пауза — кнопкой; данные прошлого обновления остаются при ошибке источника.

## 4. R215 — обращения

### 4.1. Поток обращения (Р-124)

```
new ──► open (в работе) ──► waiting (ждём человека) ──► done (решено) ──► archived (архив)
 ▲          │  ▲                 │                          │
 └──────────┴──┴─────────────────┴──────────────────────────┘   любой шаг назад разрешён владельцу
```

- `new` — пришло; `open` — взято в работу; `waiting` — ответили по контакту, ждём человека; `done` — решено
  (`resolved_at`); `archived` — убрано из ящика (`archived_at`), остаётся в поиске и в архиве до срока хранения
  (`stream.support.retention`, 6 месяцев).
- Назначение (`assignee` — свободное слово: `owner`, `gpt`, имя), приоритет (`low|normal|high|urgent`), метки
  (`tags`, слова через пробел), внутренние заметки и события (таблица `support_notes`: `note`, `reply`, `status`,
  `assign`) — лента внизу обращения.
- **Канал ответа.** Своего канала нет (человек анонимен): ответ идёт по контакту, который он оставил. Пульт
  распознаёт `@handle` → ссылка `t.me/`, e-mail → `mailto:`, телефон — текстом; «Ответил» — заметка `reply` с тем, что
  сказано, и переход в `waiting`. Если контакта нет — обращение помечено «без контакта»: решаем сами, человек увидит
  результат в продукте.
- **SLA** (`stream.support.sla.first-response` 4 ч, `sla.resolve` 48 ч): таймеры считает ядро — `firstResponseDueAt`,
  `resolveDueAt`, флаги `breached`; первый ответ — первая заметка `reply` или переход в `open`. Пульт красит просроченные.
- **Диагностика** — JSON, который человек приложил сам (версия, браузер, ОС, недавние ошибки): пульт разбирает его в
  таблицу; ошибки из него — ссылки в раздел «Ошибки» (счётчики `cord_client_errors_total` по тому же коду).
- **Связь со встречей**: «Сообщить о проблеме» (R79) приходит из встречи, но номера встречи в обращении нет и не будет
  (П8); связь — по времени: ссылка «Встречи в это время» ведёт на раздел «Встречи → За период» вокруг `created_at`.

### 4.2. Хранение (V17)

`support_tickets` + `assignee`, `priority`, `tags`, `first_response_at`, `resolved_at`, `archived_at`; `status`
расширен до `VARCHAR(16)`. Новая `support_notes(id, ticket_id, created_at, author, kind, text)`.

### 4.3. API ядра

```
GET  /api/v1/admin/support?status&topic&q&assignee&priority&before&limit   → [Entry]  (q — по тексту, контакту, номеру)
GET  /api/v1/admin/support/counts                                          → {new, open, waiting, done, archived, breached}
GET  /api/v1/admin/support/{id}                                            → {ticket: Entry, notes: [Note]}
PUT  /api/v1/admin/support/{id}/status  {status}                           → 204   (как раньше; статусы — все пять)
PUT  /api/v1/admin/support/{id}         {assignee?, priority?, tags?}      → 204
POST /api/v1/admin/support/{id}/notes   {kind: note|reply, text}           → Note  (reply → waiting, первый ответ)
```

Кнопки Telegram (`/internal/support/{id}/status`) остаются: `OPEN`/`DONE`.

### 4.4. Пульт

`GET /api/fleet/support?…` — **ящик всей системы**: служба спрашивает каждое ядро с учётными данными (стенд A, продукт
meet) и склеивает ответы, помечая `machine`; упавшее ядро — строка ошибки в ответе, остальные показываются.
`GET /api/fleet/support/counts` — счётчики по статусам сложены по машинам. Рычаги — `/core/{machine}/support/{id}…`,
каждый в журнале пульта. Экран «Обращения»: вкладки-статусы со счётчиками, фильтры (машина, тема, назначено, приоритет,
поиск), таблица с номером/темой/первыми словами/контактом/SLA/назначено; обращение — в `Drawer`: текст, контакт
(ссылка), отмеченное, диагностика, лента, действия.

### 4.5. Что ещё предложено (не сделано, в бэклог)

Шаблоны ответов; автоназначение по теме; «похожие обращения» по словам; экспорт CSV за период; автоархив `done` старше
14 дней; уведомление в Telegram о просрочке SLA через vmalert (метрика `cord_support_open{status}` добавлена — правило
алерта пишется в `infra/monitoring`); связь с выпуском клиента (версия из диагностики → «починено в 1.2.2»).

## 5. Что не делаем и почему

- Внешние аналитики (PostHog, Plausible, Matomo) — отвергнуты в `observability.md` §9: не помещаются и уносят данные.
- Метки с номером комнаты в метриках — П8 и число рядов; битрейт на встречу — оценкой из состава.
- Отдельная учётная запись «кто ответил» в поддержке — один владелец и агент; `assignee` — слово.
- Хранение ключа посетителя дольше 400 дней или связывание с адресом — нет.

## 6. Решения

- **Р-121. Личность в аналитике — HMAC-ключ профиля устройства, стабильный, со сроком 400 дней; без профиля —
  суточно-солёный отпечаток адреса без склейки между днями.** Иначе удержание и когорты невозможны (§2.3).
- **Р-122. ЛТВ — когорта по первому дню в периоде и вся её жизнь до сегодня; АКТУАЛ — всё, что было в периоде.** (§2.5)
- **Р-123. ER = звонивших / посетителей; stickiness = среднее дневное активных / различных за период; удержание D_N =
  вернулся в течение N дней (нестрогое).** (§2.6)
- **Р-124. Статусы обращений: new → open → waiting → done → archived; SLA 4 ч / 48 ч; ответ — по контакту человека,
  заметкой `reply`.** (§4.1)
- **Р-125. «Флот — live» — групповые запросы к VictoriaMetrics на весь флот раз в 5 с, раскладка по меткам машин; ядро
  спрашивается только о составе встреч.** (§3.1)
- **Р-126. `X-Cord-Client` — тип клиента словом из перечисления во всех запросах веба; ОС — из `User-Agent` словом.**
  (§2.9)

## 7. Выкатка (главная сессия)

1. Ядро продукта на meet и ядро стенда A: образ с V16 и V17 (Flyway применит при старте; обе миграции только добавляют —
   откат образа работает, лишние столбцы и таблицы не мешают). `ANALYTICS_RETENTION` и `SUPPORT_SLA_*` — по
   умолчанию, в `.env` не нужны.
2. Веб (тот же бандл: продукт и пульт): заголовок `X-Cord-Client`, событие `visit`, три экрана пульта.
3. Служба `fleet` на A: `/live`, `/support`, чтение `analytics`.
4. Бот Telegram не меняется.

Порядок важен только между 1 и 2 на одной машине: веб с `POST /api/v1/visit` против старого ядра получит 404 и молча
проглотит; старый веб против нового ядра работает как раньше.
