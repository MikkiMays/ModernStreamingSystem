# Ядро Cord: оптимизация и горизонтальный рост (R236)

Статус: **проект, принят к разработке** 12.11.2026. Продолжает `scale-1000.md` (замеры И1–И5 и перечень узких мест
остаются в силе, кроме снятого R228 общего предела встреч) и опирается на построчное чтение ядра 12.11.2026
(`server/src/main` — 131 файл, 26 968 строк; тесты — 54 файла, 545 тестов). Решения — Р-152…Р-158 (§8).

## 1. Вопрос владельца: переписать Java на Rust?

Коротко: **ядро целиком — нет, не сейчас; новые службы, где Rust даёт выигрыш без риска для встреч, — да, уже в этой
волне.**

Что измерено и прочитано:

| Факт | Откуда |
| --- | --- |
| Звук и видео идут клиент ↔ медиаузел (LiveKit, Go) ↔ клиент; ядро в этом пути не стоит. Доля языка ядра в задержке разговора — ноль | `MediaGateway.token`, `docs/architecture.md` |
| На одно сообщение чата в комнате из 20 человек ядро делает ≈ 86 транзакций и ≈ 50 чтений с разбором всего JSON комнаты; затем 20 браузеров перечитывают полный снимок с перепиской до 1000 сообщений | замер И2, `RoomSocket.java:262-288`, `RoomService.java:2162-2186`, `meeting.ts:445-447` |
| Каждый вход берёт один замок на всю систему и разбирает все строки встреч, при создании — дважды | замер И3, `RoomService.java:117, 136, 759` |
| В простое ядро переписывает каждую открытую комнату раз в 2 с без изменений и раз в секунду запирает каждую строку встреч, включая закрытые | замер И4, `MediaService.java:349`, `MediaReconciler.java:47-53` |
| Половину ЦП под нагрузкой тратит не ядро, а PostgreSQL — на те же лишние чтения и записи | замер И2: 1,44 ядра JVM + 0,75 ядра базы |

Это устройство, а не язык. Тот же алгоритм на Rust дал бы примерно ×1,5–3 по ЦП ядра и в 5–10 раз меньше памяти —
но квадратичный рост по размеру комнаты и походы в базу остались бы. Исправление устройства даёт ×10–50 на любом языке.
Переписать 20 тысяч строк логики (правила четырёх игр, права, сроки, защита, обращения, доска) и 545 тестов с
побайтным сохранением формата комнаты в базе и контракта API — месяцы работы и главный источник новых ошибок в продукте,
который уже работает.

Где Rust оправдан сейчас — и применяется:

| Служба | Почему Rust |
| --- | --- |
| `cord-agent` — агент управления на каждой машине (`control-plane.md`) | один статический файл без среды исполнения, 5–10 МиБ памяти на узле с 2–4 ГБ; мало кода, высокая цена ошибки |
| `insight` — приём и подсчёт аналитики (`analytics-v2.md`) | новый код без наследства; поток событий, хэши и разбор — работа процессора; отделён от встреч: сбой аналитики разговору не мешает |

Когда вернуться к вопросу о ядре: после шагов §3 повторить замеры И2–И4. Если ядро на целевой нагрузке всё ещё тратит
больше одного ядра ЦП или его память и время запуска (≈ 600 МиБ, 25–30 с) мешают на выбранных серверах — выносить в
Rust по частям, начиная с рассылки событий (граница к тому времени будет чистой: готовые представления и патчи, §3.3).

## 3. Шаги

### 3.1. Быстрые правки (часы)

| Что | Где |
| --- | --- |
| Сверка медиа пишет комнату только при изменении | `MediaService.observe` |
| Убрать запись ключа `control:<участник>` в Redis раз в 10 с на каждый сокет — его никто не читает | `RoomSocket.presence` |
| Страховочный проход сокетов раз в 15 с — без чтения базы для сокетов, у которых номер события не отстал | `RoomSocket.sweep` |
| Карты `sequences` и `previewAt` чистятся при закрытии комнаты | `RoomService` |
| Индекс по сроку сообщений и раздельные удаления | миграция, `Lifecycle.sweepLedger` |
| Планировщик: потоков по числу задач, долгие проходы не задерживают часы игр | `RuntimeConfig` |
| Шлюз сжимает ответы `/api` | `infra/Caddyfile` |
| PostgreSQL: `shared_buffers`, `effective_cache_size`, `wal_compression=zstd`, `max_wal_size`, `checkpoint_timeout`; `fillfactor` 80 у `rooms` | `compose.yaml`, миграция |
| SFU: `mem_limit` по памяти машины и `GOMEMLIMIT` | `compose.yaml`, `compose.node.yaml` |

### 3.2. Вход без общего замка

- Столбцы `rooms.closed_at`, `created_by` (хэш профиля), `created_from` (отпечаток адреса) и индексы по ним; уникальный
  индекс по коду встречи — код выбирается вставкой с повтором при совпадении, а не подсчётом под замком.
- Таблица мест `seats(room_id, profile_hash, member_id, since)` с индексом по профилю: «один профиль — одна встреча»
  проверяется запросом по индексу под `pg_advisory_xact_lock(хэш профиля)`, а не разбором всех комнат.
- «Сколько открытых встреч у адреса и профиля» — счётчик по индексам.
- Общий замок остаётся только там, где он действительно про всё сразу: окна технических работ.
- Избранное и вложения — замок профиля или комнаты; `DELETE /favorites/{id}` проверяет профиль и предел **до** любого
  замка (сейчас этим путём посторонний может занять все соединения с базой).

### 3.3. Рассылка: снимок один раз, дальше — патчи

Сейчас: событие → каждый сокет сам читает комнату и журнал событий из базы → каждый браузер заново качает полный снимок
по HTTP.

Будет:

1. Команда, как и сейчас, меняет комнату под замком её строки и пишет один раз. **Перед отпусканием замка** ядро
   строит представление комнаты для каждого участника, у которого есть сокет (`snapshotFor` — у игр оно разное: чужих
   карт в нём нет), и кладёт в память вместе с номером события: `RoomCache`.
2. Сокет хранит последнее отправленное представление. Рассылка берёт новое из памяти, считает разницу (JSON Patch,
   RFC 6902) и шлёт пакет `patch {sequence, base, ops}`; первый раз и при разрыве номеров — полный `snapshot`. Базу
   рассылка не трогает вовсе.
3. Браузер применяет патч к своему снимку (`meeting.ts`); полный снимок запрашивает только если `base` не совпал.
4. Переписка уходит из снимка: новое сообщение приходит событием (оно уже несёт текст), история грузится отдельной
   ручкой страницами при открытии чата.
5. События для звуков и уведомлений идут как сейчас, но сериализуются один раз на комнату, а не на сокет.
6. Сокет на другом экземпляре ядра (когда их станет два) будит Redis, и он идёт прежним путём через базу — правильно,
   просто медленнее; владение комнатой (§5) убирает и это.

Цена на событие в комнате из N человек: одна транзакция и N раз «построить представление, сравнить, отправить» в
памяти — доли миллисекунды на участника вместо десятков запросов.

### 3.4. Фоновые проходы — только по открытым комнатам

- Сроки: запрос по индексу «открытые комнаты с наступившим сроком», а не замок каждой строки раз в секунду.
- Сверка с медиаузлом: `ListRooms` узла раз в 2 с; `ListParticipants` — параллельно и только для комнат, где состав
  изменился (вебхук LiveKit или расхождение счётчика); полная сверка — раз в 15 с.
- «Сейчас» для пульта и метрики — по открытым комнатам из индекса.

### 3.5. Доска и картинки

Курсоры — одной пачкой раз в 50 мс; очередь сокета 1–2 МиБ; картинки — файлами в томе загрузок с `Cache-Control:
immutable` (имя — хэш содержимого), а не `BYTEA` через память ядра.

## 4. База данных

Архитектуру менять не нужно — нужно перестать её перегружать (§3) и добавить то, чего нет вовсе:

| Что | Решение |
| --- | --- |
| Движок | PostgreSQL 18 остаётся: данных мало (гигабайты), нагрузка после §3 — сотни транзакций в секунду |
| Состояние комнаты | один JSON в строке остаётся источником правды; представления и патчи — в памяти ядра |
| Аналитика | своя схема `insight`, события разделами по месяцам; встречам не мешает |
| Отказ машины | потоковая реплика на второй машине в другом дата-центре, повышение скриптом: потеря — секунды, простой — минуты |
| Копии | сейчас их нет совсем — главный риск данных. Ночная копия метаданных до года и копия с журналом не дольше суток (содержимое живёт сутки, Р-134) — на вторую машину и в объектное хранилище |
| Redis | пределы, «разбуди сокеты», аренда лидера фоновых задач; данных, которые жалко потерять, в нём нет |
| Что не нужно | шардирование, распределённые базы, Kafka — на этих объёмах только лишние точки отказа |

## 5. Несколько ядер и несколько дата-центров

**Медиа уже распределено**: встреча живёт на одном узле, узлов сколько угодно, в любых городах; узел выбирается по
замеру человека и нагрузке, упавший узел эвакуируется за секунды. Рост по людям — это число медиаузлов.

**Ядро**: одно активное и один горячий резерв в другом дата-центре — этого хватает до нескольких тысяч одновременных
после §3. Второй *активный* экземпляр нужен для выкатки без перерыва и для десятков тысяч; к нему ведут пять вещей,
каждая отдельным шагом:

1. Владение комнатой: шлюз направляет сокеты и команды комнаты на один экземпляр по хэшу её номера.
2. Лидер фоновых задач: аренда в Redis, проходы выполняет один экземпляр.
3. Состояние из памяти — в общее место: рычаг дренажа, превью экрана, решение «узел мёртв», резервы размещения.
4. Наблюдатели (журнал участников, статистика встреч) — функции от состояния комнаты, а не от того, что видел процесс;
   аналитика уже вынесена в `insight`.
5. Вложения — в объектное хранилище вместо тома одной машины.

Активные ядра в разных странах с одной базой не нужны и вредны: задержка до базы умножится на каждую транзакцию.
Регион — это медиаузлы; ядро и база — в одном месте, рядом с большинством людей.

## 6. Защита от роботов в ядре

| Дыра (12.11.2026) | Правка |
| --- | --- |
| `DELETE /favorites/{id}` без предела берёт общий замок даже с мусорным профилем | проверка профиля и предел до замка (§3.2) |
| Сокет событий не закрывается на `auth` с несуществующей комнатой — можно слать `auth` раз за разом | закрывать на любой отказ `auth`, предел попыток |
| Автоблок считает любой код `RATE_LIMITED`, в том числе пределы участника, и может закрыть целый офис или мобильную сеть | считать только отказы пределов по адресу |
| Задача «не робот» стоит скрипту миллисекунды | цена 250 000 по умолчанию (доли секунды в браузере), ×4 и ×8 под давлением — как сейчас |
| Потолок обращений в поддержку — 60 в час на весь сервер: один скрипт выключает форму всем | предел по адресу перед общим |
| Отказ входа создавал «нового посетителя» | прежняя аналитика удалена; отказы считаются итогом минуты (`refusal`) |

## 8. Решения

- **Р-152. Ядро на Rust не переписывается; на Rust пишутся `cord-agent` и `insight`.** Пересмотр — по замерам после §3.
- **Р-153. Рассылка — представления в памяти и патчи RFC 6902; полный снимок — только при входе и разрыве номеров.**
- **Р-154. Вход — таблица мест и замок профиля; общий замок системы с дверей входа, избранного и вложений снимается.**
- **Р-155. Фоновые проходы — только по открытым комнатам из индекса.**
- **Р-156. База — PostgreSQL с потоковой репликой в другом дата-центре; аналитика — в своей схеме.**
- **Р-157. Ядро — одно активное и горячий резерв; регионы — медиаузлами.**
- **Р-158. Цена задачи «не робот» — 250 000; автоблок — только по пределам адреса.**
