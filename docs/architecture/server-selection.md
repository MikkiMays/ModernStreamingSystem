| Что выбирает «Авто» и по чьему замеру? | Узел с лучшим измеренным путём **с устройства создателя** в момент «Создать встречу», с учётом свободного места на узлах. Так же делает Discord: регион «Automatic» задаёт первый вошедший в пустой канал [источник 1, 2]. Взвешивать по всем участникам нельзя — в момент размещения их ещё нет; после — нельзя трогать идущую встречу. | §3.1 |

Создатель с VPN → узел ближе к выходу VPN (`fra`/`hel`), москвичи ходят туда (≈ 40 мс). **Миграции нет ни в одном случае.** Ведущий может перевести встречу руками. | §3.2 |

Встречу двигают только два события: смерть узла и ручной перевод ведущим. | §3.3 |
| Узел перегружен — распределять? | Только **при размещении новых** встреч: занятые места, люди, ЦП со steal и отдача канала — ступень 1–4 на каждый узел, запас 25 % под рост идущих встреч. У нас: плановый переезд — **make-before-break** через второе подключение (§4): звук ≈ 0,2–0,5 с, картинка без чёрного кадра, показ экрана без потери; отказ узла — с ≈ 15 с до **≈ 6–8 с** (§5). | §2, §4, §5 |
| Как быстро? | Размещение — 0 мс сверх обычного входа (замер идёт в фоне; ждём ≤ 400 мс только без результата). Ручной перевод — 2–4 с подготовки без разрыва + ≈ 0,3 с переключения. Отказ узла — цель ≤ 8 с до звука у всех (сейчас 15,5 с [измерено]). | §3.6 |
| Кто может сменить сервер во встрече? | **Создатель встречи** (роль `CREATOR`, `Permissions.java`) — как в серверах Discord («admins only») [источник 5]. Остальные видят узел и флаг, получают уведомление «Ведущий переводит встречу в Хельсинки». | §3.5 |
| Что с `cordcam.ru`, `callcord.ru`, `nikg.tech`? | Продукт и все узлы — под `cordcam.ru`: `cordcam.ru` (ядро, A), `fra.`/`rtc-fra.`/`turn-fra.` (A), `hel.`/… (B), `msk.`/… (сервер cordcam), `fra2.`/… (сервер meet). `callcord.ru` — редирект, затем не продлевать. `cord.nikg.tech` — 301 с переносом настроек 30 дней, потом удалить. `meet.nikg.tech` — 301 на `cordcam.ru`, машина становится узлом `fra2`. | §6, §7 |

## 2. Как это делают другие — факты и выводы

### 2.1 Discord

**Документированные факты.**

- Регион голосового канала — поле `rtc_region` канала; `null` = «automatic» [источник 1: «voice region id for the voice
  channel, automatic when set to null»]. Список регионов — `GET /voice/regions`; у региона флаг `optimal` — «true for a
  single server that is closest to the current user's client» [источник 1], то есть Discord **сам мерит близость с
  клиента** и подсказывает один «оптимальный» регион.
- В режиме «Automatic» регион задаётся **первым человеком, вошедшим в пустой канал**, и **не меняется, пока люди
  приходят и уходят**; сбрасывается, когда канал опустел [источник 2, FAQ Discord; подтверждено независимыми
  пересказами 4, 5]. Это ровно модель «регион фиксируется на жизнь встречи».
- Смена региона канала руками — право администратора сервера; в личных и групповых звонках менять может любой
  участник [источник 4, 5]. Эффект для всех: «Everyone in that channel will briefly disconnect and reconnect to the new
  location» [источник 5]; «after a brief period (usually less than one second) of interruption» [источник 4]. На
  уровне протокола это событие `VOICE_SERVER_UPDATE` с новым `endpoint` — старый голосовой WebSocket закрывается кодом
  4000, клиент заново проходит рукопожатие через ≈ 1 с [источник 6: журнал бота при смене региона
  `southafrica… → singapore…`]. То есть **смена региона у Discord — это break-before-make**: разрыв и повторный вход, не
  бесшовный перенос.
- Отказ голосового сервера: «Sent … when the current voice instance fails over to a new server. A null endpoint means
  that the voice server allocated has gone away and is trying to be reallocated. You should attempt to disconnect from
  the currently connected voice server, and not attempt to reconnect until a new voice server is allocated» [источник 7].
  Механика 2018 года: серверы шлют здоровье и загрузку в etcd; гильдии назначается **наименее загруженный сервер её
  региона**; при отказе клиент замечает обрыв голосового WS и просит «voice server ping» через шлюз, «Discord Guilds
  server confirms the failure… assigns a new Discord Voice server… pushes all the voice state objects to the new voice
  server… Every client is notified about the new voice server and creates a voice WebSocket connection» [источник 3].
  Падение одного SFU-процесса (не машины) — «minimal service interruption (few dropped packets)» [источник 3].
- 2025: «We pick one SFU instance to host an entire call, and every participant connects to that one host for the call's
  entire duration» [источник 8]. Выигрыш Франкфурта «ping −34 %, packet loss −42 %» получен переносом SFU на edge
  Cloudflare и пирингом, а не каскадом [источник 8].

**Чего в документации Discord нет — и что мы из этого выводим.**

- Нигде не описан **автоматический перенос идущего звонка** ради качества. Пересказы вроде «если регион Automatic и
  есть проблемы, система сама переместит вас» [источник 2 в пересказе 4] не подтверждены ни блогом 2018, ни 2025, ни
  API; единственный документированный автоматический переезд — **отказ сервера** (`VOICE_SERVER_UPDATE` с `null`, затем
  новый endpoint) [источник 7]. **[вывод]**: Discord фиксирует сервер на звонок, двигает его только при отказе или по
  руке администратора, и оба случая — через разрыв и повторный вход, короткий (≈ 1 с) потому, что сигнальный путь у них
  свой и быстрый, а не потому, что медиа переносится без разрыва.
- «Automatic» у Discord **не** взвешивает местоположение всех участников — регион задаётся первым вошедшим [источник
  2]. Утверждение «определяет, где большинство участников» [источник 5] противоречит FAQ и, по-видимому, ошибочно.

### 2.2 Zoom

- Клиент направляется геолокацией в ближайший ЦОД, назначается на наименее загруженный MMR; MMR сгруппированы в
  Meeting Zones с контроллерами зон и глобальным контроллером [источник 9]. Отказоустойчивость — «active-active
  connectivity to failover data centers, zone controllers, and multi-media routers»; сроки переключения и опыт
  участника не описаны [источник 9]. Каскад между MMR — для больших/гибридных встреч («cascaded traffic paths for large
  enterprises») [источник 9]. **[вывод]**: балансировка — при размещении; идущую встречу ради нагрузки не трогают;
  каскад — инструмент масштаба, не задержки.

### 2.3 Google Meet

- Открытой документации по размещению и переезду нет; известны региональные медиасерверы и SVC (T09 §11). Публичные
  разборы — реконструкции, не первоисточник [источник 10]. Берём только то, что у них видно глазами: смена сети у
  одного участника чинится у него одного (ICE restart), встреча остаётся там, где была.

### 2.4 LiveKit Cloud (закрытая часть нашего SFU)

- Каждый участник подключается к ближайшему серверу, медиа одной комнаты ретранслируется между серверами (mesh)
  [источник 11]. Для отказов сервера они сделали **live migrations**: «Live migrations perform an ICE restart on the
  client side, but point to a different server. The new server examines the state the participant is expected to be in,
  and reconstructs its local (server) state… the disruption caused by a server-side failure is reduced to under a
  second!» [источник 11]. Это требует общего состояния между серверами и закрытого кода — в OSS 1.13.6 этого нет
  (`distributed-media.md` §3) [код]. **[вывод]**: «< 1 с» у LiveKit Cloud — ориентир для нашего **планового** переезда
  (§4), где мы можем подготовить второе подключение заранее и получить разрыв ещё меньше; для отказа узла в OSS такой
  скорости не достичь — минимум стоит обнаружение.

### 2.5 Jitsi (Octo)

- Каскад между мостами по регионам; внутри близких регионов мосты объединены в группы, потому что каскад на малом
  расстоянии **повышал** RTT [источник 12]. Уже учтено в R195 §0: каскад не для разговоров Европа–Европа.

## 3. Политика Cord — решено

### 3.1 «Авто»: что выбирается и по чьему замеру

**Решение (Р-100).** Узел новой встречи выбирает ядро по замеру пути **с устройства создателя** в момент создания
(`node-probe.ts`, как в 1.2.1) и по **ступени нагрузки каждого узла** (§3.4). Замеры входящих в выбор не участвуют;
узел встречи зафиксирован на её жизнь.

Почему не «по всем участникам» и не «взвешенно»:

1. В момент размещения участников нет — есть создатель. Любой «перевыбор, когда вошёл второй/третий» — это переезд
   идущей встречи ради задержки, то есть ровно то, чего владелец не хочет («никаких спрыгов»). Discord поступает так же
   [источник 2].
2. Взвешенный выбор дал бы выигрыш только когда создатель далеко от всех остальных (§3.2). Для этого случая есть ручной
   перевод ведущим (§3.5) — без разрыва (§4). Автоматика здесь всегда рискует «мигающим VPN» одного человека.
3. Узел создателя почти всегда и есть лучший для группы: люди из одной компании/города собираются вместе.

Что меряется (без изменений, [код] `node-probe.ts`): TCP-оборот до `probeUrl` узла (медиана трёх), UDP-оборот одним STUN
до TURN узла; узлы с открытым UDP впереди; гистерезис 15 мс и 30 % против прошлого выбора; кэш 60 с; память суток.
Новое: ядро **снимает** с замера узел, чья ступень нагрузки 4 («мест нет») или который на дренаже, и понижает узел со
ступенью 3, если есть узел не хуже чем на 20 мс со ступенью ≤ 2 (§3.4).

**Ручной режим (Р-101).** В «Настройки → Сервер» по умолчанию «Авто»; ниже — список узлов с флагом, городом, замером и
ступенью нагрузки. Выбранный вручную узел:

- вне встречи — применяется к **следующей** встрече, которую создаст этот человек, и запоминается на устройстве до
  возврата на «Авто» (на главной видно «Сервер: 🇫🇮 Хельсинки · вручную — сбросить»); входящий по ссылке никак не
  влияет на узел чужой встречи;
- во встрече — **переводит эту встречу** (только создатель, §3.5); после перевода узел встречи зафиксирован заново;
- если выбранный узел мёртв или полон — ядро берёт лучший по замеру и говорит об этом («Хельсинки занят — встреча
  создана во Франкфурте»), а не отказывает.

### 3.2 Двое в Москве, один через VPN в Нидерландах

Узлы для примера: `msk` (Москва, сервер cordcam), `fra` (A), `hel` (B).

| Кто создал | Что намерил | Узел | Что у остальных | Миграция |
|---|---|---|---|---|
| Москвич | `msk` 3–8 мс, `hel` ≈ 20–25, `fra` ≈ 39 [оценка, T09] | `msk` | второй москвич — 3–8 мс; человек с VPN: его пакеты идут из Амстердама в Москву, ≈ 45–60 мс + задержка VPN; UDP зависит от VPN | **нет** |
| Человек с VPN (выход — Амстердам) | `fra` ≈ 8–12 мс, `hel` ≈ 25–30, `msk` ≈ 45–60 | `fra` | москвичи — ≈ 39 мс до Франкфурта (как сегодня) | **нет** |
| Любой, но ведущий решил иначе | — | ручной выбор | все переходят make-before-break (§4) | по руке |

Где здесь «несправедливость»: во втором случае двое из трёх получают 39 мс вместо 5. Это цена фиксированного узла и
честный компромисс: 39 мс — качество сегодняшнего Cord, которое владелец считает приемлемым; автоматика, которая бы
«исправила» это переездом, через минуту переехала бы обратно, когда третий выключит VPN. Если группа постоянно
собирается так — создаёт встречу москвич или ведущий один раз выбирает `msk` вручную.

### 3.3 VPN посреди встречи — переезжать?

**Решение (Р-102). Никогда автоматически.** Идущую встречу переносят только: (1) отказ узла (§5); (2) ручной перевод
создателем (§3.5); (3) дренаж узла перед работами — **только** через тот же плановый механизм (§4) и только с
подтверждением оператора (`node.sh <узел> drain --move` ждёт конца встреч по умолчанию; `--move` переносит их тёплым
переездом, окно работ — как сегодня, без встреч).

Почему:

- VPN одного человека меняет **его** путь, не встречу. Для его пути уже есть лестница R195 §6.4: resume (1–2 с) → ICE
  restart → TURN/TLS 443 узла комнаты. Остальные не замечают ничего.
- Автоматический переезд всей встречи «на лучший узел» дал бы выигрыш одному и разрыв всем; мигающий VPN — серию
  разрывов. Так не делает ни Discord [источник 2, 7], ни Zoom [источник 9].
- «Лучший узел» для группы с VPN не определён: VPN-выход может быть ближе к одному узлу, а трафик остальных — к другому.

Что мы **делаем** для человека с VPN: показываем в диагностике его путь («через TURN · TLS», «UDP закрыт») и замер до
узлов; если встреча ещё не началась (создатель один, второго участника нет — `room.startedAt == null` [код
`RoomState.markStarted`]), создатель видит мягкую подсказку «Ближе — Хельсинки (12 мс против 41). Перенести?» — одна
кнопка, никаких автодействий (R195 §6.4 п. 6, теперь через §4).

### 3.4 Перегрузка: балансировка только при размещении

**Решение (Р-103).** Ступень нагрузки узла 1–4 считается **ядром** по данным узла раз в 5 с (вместе с `ListRooms`):

| Доля | Откуда | Примечание |
|---|---|---|
| занятые встречи / `maxRooms` | `ListRooms` узла (есть) | как сегодня `full()` |
| люди на связи / (`maxRooms` × 6) | `ListRooms` → `num_participants` | «обычная встреча 5–6 человек» (Р-37) |
| ЦП хоста со steal | node-exporter узла по магистрали (есть в scrape) → ядро читает те же ряды из VictoriaMetrics **или** узел отдаёт `GET /api/v1/load` сам (`gateway-lite` → маленький обработчик `LoadMeter` без ядра) | предпочтительно второе: ядро не должно зависеть от мониторинга |
| отдача канала / `uplinkMbps` узла | то же | `uplinkMbps` — новое поле реестра |

Ступень = наибольшая доля по четвертям (правило `LoadMeter` [код]), вверх сразу, вниз через 30 с. **Запас**: узел не
получает новую встречу, если после неё прогнозная доля превысит **75 %** (новая встреча считается за 6 человек и 25
Мбит/с) — это и есть «headroom» под рост идущих встреч. Ступень 4 — не ставить вовсе. Выбор среди подходящих — по
замеру создателя, при равенстве (± 20 мс) — менее загруженный.

**Узел заполнился посреди встречи, а люди входят.** Вход **не отказывается** из-за нагрузки узла: встреча там, где она
есть, и её участники важнее новых встреч. Что происходит:

1. SFU LiveKit сам снижает слои simulcast и ставит видео на паузу слабым подписчикам (`allow_pause`, R119) — это
   деградация картинки, не разрыв.
2. Ядро перестаёт ставить на узел новые встречи (ступень ≥ 3 с запасом), алерт `NodeSaturated{node}` (новый, ступень 4
   ≥ 60 с).
3. Создатель видит в настройках ступень узла («🇫🇮 Хельсинки · тесно») и может перевести встречу тёплым переездом (§4)
   на свободный узел. Автоматики нет — Р-102.
4. Предел числа участников комнаты (`max-participants`) остаётся как есть — это правило продукта, не нагрузки.

**Дренаж перед выкаткой** — как сегодня (`enabled: false` → новые встречи не ставятся, ждём конца идущих) плюс
возможность `--move` (§3.3).

### 3.5 Ручной перевод встречи: кто, что видят, как показано

**Решение (Р-104).**

- **Кто**: создатель встречи (`Permissions.Role.CREATOR`, право не передаётся [код `Permissions.java:32`]). Как в
  серверах Discord — только администратор [источник 5]. Остальным — только просмотр. В личных звонках Discord менять
  может любой [источник 4], но у нас любая встреча — «комната с ведущим», и право на действие, которое на секунду
  трогает всех, должно быть у одного.
- **Где**: «Настройки → Сервер» во встрече — тот же список, что и вне встречи: радио «Авто (узел выбран при создании:
  🇩🇪 Франкфурт)» и узлы «🇫🇮 Хельсинки · 12 мс · ▮▮▯▯ свободно», «🇷🇺 Москва · 38 мс · ▮▮▮▯ тесно». У создателя узлы —
  кнопки «Перевести сюда»; у остальных — текст. Узел на дренаже или ступени 4 — серый, «мест нет».
- **Что видят остальные**: плашка на 3 с «Ведущий переводит встречу в 🇫🇮 Хельсинки…», затем «Готово · 🇫🇮 Хельсинки».
  Пока идёт подготовка (§4) — ничего не рвётся; переключение — ≈ 0,3 с звука. В диагностике сверху меняется флаг.
- **Ограничения**: не чаще раза в 60 с на встречу (гистерезис от «а давайте попробуем ещё»); нельзя во время
  восстановления встречи (`RECOVERING` у кого-то) и во время другого перевода; нельзя на узел ступени 4 или на дренаже.
- **Флаги**: по полю `country` реестра (ISO 3166-1 alpha-2: `DE`, `FI`, `RU`), рисуются эмодзи-флагом региональных
  индикаторов (`String.fromCodePoint(0x1F1E6 + …)`); на Windows эмодзи-флаги не отображаются шрифтами системы — там
  `web/src/ui/kit/Flag.tsx` рисует SVG-флаг из `brand/flags/<cc>.svg` (три-четыре файла) с запасным текстом «FI».
- **Загрузка**: `LoadBars` (есть, R143) по ступени узла из `GET /api/v1/nodes` (новый ответ, §8.3), обновление раз в
  10 с пока открыты настройки.

### 4.2 Протокол переезда

Участники: ядро (**координатор**), клиенты (**исполнители**), два узла (ничего о переезде не знают).

```
создатель: POST /api/v1/rooms/{id}/media/move {to:"hel"}             ядро: проверки §3.5
ядро → всем: room.changed, snapshot.mediaMove = {id, to, phase:"prepare", deadline:+6s}
каждый клиент:                                                      (старое соединение живёт)
  token B ← GET /token?move=<id>      (url узла hel; forward_auth на hel пускает по mediaNodeNext)
  roomB.connect(urlB, tokenB, {autoSubscribe:false})
  publish на B: clone(mic) [всегда], clone(camera), clone(screen) [если канал позволяет, иначе после switch]
  subscribe на B на дорожки тех, кто уже там; вывод — в скрытые элементы (видео декодируется, звук muted)
  POST /media/move/{id}/ready {audio:true, video:true|false}
ядро: все CONNECTED участники ready  ИЛИ  deadline → phase:"switch"  (+ mediaNode=to, mediaMoves++ **без RECOVERING**)
каждый клиент при phase:"switch":
  звук: unmute B-элементов, mute A-элементов (один кадр)   → переключение ≈ 1 период джиттер-буфера
  видео/экран: показать B-элементы вместо A (тот же слот сцены); если B-видео ещё нет — держать последний кадр A
  roomA.disconnect(false)   (дорожки не останавливать — они и так клоны; остановить клоны A)
  POST /media/move/{id}/done
ядро: все done или +5 с → phase:null, журнал «room … moved fra→hel in 2.8 s, gaps: audio 240 ms p95»
опоздавшие (не ready к deadline): как сегодня — relocate() по mediaMoves (разрыв 2–5 с только у них)
```

Почему переключение по **команде ядра**, а не каждый сам: иначе первые перешедшие слышат на B тишину, пока остальные
ещё на A. Ядро ждёт всех (или 6 с) и переключает всех одним событием — разрыв у всех одинаковый и короткий.

### 4.3 Что меняется в ядре

- `RoomState.mediaMove` (`@JsonInclude(NON_NULL)`): `{id, from, to, phase, deadline, ready:[participantId], startedAt}`.
  `mediaNodeNext` — то же `to`.
- `POST /rooms/{id}/media/move` — право `MEDIA_MOVE` в `Permissions` (CREATOR); проверки §3.5; создаёт `mediaMove`,
  `room.changed`. Ядро **явно создаёт комнату** на узле-цели (`CreateRoom` Twirp; сегодня комната создаётся первым
  входом — для переезда полезно задать `max_participants`, `empty_timeout` заранее).
- `GET /token?move=<id>` — тот же `MediaToken`, но `url` узла `to`; `authorizeSignaling` принимает `X-Media-Node == to`,
  пока `mediaMove` жив.
- `POST …/ready`, `POST …/done` — отметки; переход `prepare → switch` — когда все `CONNECTED` отметились или по
  `deadline` (6 с), выполняется планировщиком ядра (тот же тик, что `NodeHealth`, или отдельный `MediaMoves` раз в 500 мс).
- `switch`: `mediaNode = to`, `mediaMoves++`, статусы **не** трогаются (в отличие от `moveRoom` при смерти узла), вебхуки
  узла `from` (`participant_left`) **игнорируются** на время `mediaMove` (иначе ядро поставит `RECOVERING` тому, кто
  штатно ушёл с A). Вебхуки `participant_joined` с узла `to` — обычные.
- Таймауты: `prepare` ≤ 6 с, `switch → done` ≤ 5 с; по истечении `mediaMove = null`, остальное — обычное восстановление.
  Если к `deadline` готовых **меньше половины** — переезд **отменяется** (`phase:"abort"`, клиенты закрывают B), встреча
  остаётся на A, создатель видит «Не удалось перевести — узел Хельсинки недоступен для части участников».
- Метрики: `cord_media_move_total{result}`, `cord_media_move_seconds` (prepare, switch), `cord_media_move_gap_ms`
  (по отчётам клиентов в `done`: пауза входящего звука по `inbound-rtp`).

### 4.4 Что меняется в клиенте (`web/src/media`)

- `session.ts`: сегодня один `this.room`. Появляется `MoveCoordinator` (новый модуль `media/move.ts`): держит `roomB`,
  клоны дорожек, таблицу «слот сцены → дорожка A / дорожка B», обрабатывает фазы. `session.ts` подписывается на
  `snapshot.mediaMove` рядом с подпиской на `mediaMoves` (`relocate`).
- Публикация клонов: те же параметры кодека и битрейта (`profiles.ts`), **но** если оценка исходящего канала
  (`link-quality.ts`, `outbound-note.ts`) ниже 2× нужного — камера и показ на B публикуются **после** switch
  (видеоразрыв ≈ 0,5–1 с только у этого человека, звук всё равно без разрыва).
- Переключение воспроизведения: `playout.ts` получает `swap(trackA → trackB)` — тот же элемент, новая дорожка;
  видео-слоты сцены — через существующий «последний кадр вместо черноты» (Р-94) на случай, если B-кадр не успел.
- Старое соединение: `roomA.disconnect(false)` после switch; клоны A — `stop()`; оригинальные дорожки (камера, микрофон,
  экран) живут дальше, теперь опубликованы в B.
- Electron и Android используют тот же код веба — отдельной работы нет (кроме проверки двойного кодирования на слабых
  машинах, §8.6).

### 4.6 Чего этот механизм не делает

- Не переносит **одного** участника на другой узел (комната целиком на одном узле — R195 §5.3).
- Не спасает от **отказа** узла (§5): нет A — нечего держать параллельно.
- Не делает перевод чаще раза в 60 с и не делает его автоматически (Р-102).

## 5. Отказ узла: с 15 с до ≈ 6–8 с без ложных переездов

### 5.1 Куда уходит время сегодня [измерено 08.11, журнал R195]

| Этап | Сейчас | Откуда |
|---|---|---|
| SDK клиента замечает обрыв (нет pong по сигнальному WS) | 9,4 с → `recovering` | `ping_timeout`/`ping_interval` приходят от SFU в `JoinResponse` (`SignalClient` [код `:18936`]); клиент начинает resume к **мёртвому** узлу — впустую |
| Ядро объявляет узел мёртвым | 14,6 с | `NodeHealth`: период 5 с + таймаут 1 с × 3 промаха [код] |
| Клиенты получают `room.changed` (`mediaMoves`↑) → `relocate` → токен → `connect` на новый узел | +0,9–1,0 с | [измерено] 15,5–15,6 с итого |

Вывод: почти всё время — **обнаружение ядром**; вход на новый узел занимает секунду.

### 5.2 Решение (Р-105): два независимых признака, порог ≈ 5 с

Опрос `ListRooms` — раз в **2 с**, таймаут 1 с. Узел считается мёртвым, когда выполнено **одно из**:

| Правило | Время | Защита от ложного срабатывания |
|---|---|---|
| **A.** ≥ 2 промаха опроса подряд **и** за последние 5 с от ≥ 50 % подключённых участников его комнат пришло `media.lost` (клиенты уже шлют `reportConnection('media.lost')` [код `session.ts:2170`]) | ≈ 4–6 с | зависание хоста B (steal) без потери медиа у людей не даёт второго признака; обрыв **магистрали** (фильтр A режет TCP) — тоже: люди на связи, признака B нет |
| **B.** ≥ 4 промаха подряд (≈ 8–12 с) при **отсутствии** подключённых участников на узле, либо при невозможности судить | ≈ 10 с | как сегодня, чуть быстрее; нечего ломать — комнат с людьми нет |
| **C.** опрос отвечает, но ≥ 50 % участников узла ≥ 20 с в `media.lost` без восстановления | 20 с | путь к узлу мёртв для людей, а не для магистрали (UDP/443 к узлу заблокирован у провайдера) — редкий случай, медленный порог против массового VPN-мигания |
| **Магистраль упала, люди в порядке** (промахи опроса, `media.lost` нет) | — | узел помечается `unreachable`: новые встречи не ставятся, идущие **не трогаются**, алерт `BackboneDown`; эвакуация — только когда появится признак от людей (A) |

Почему так безопасно для B с его steal: зависание хоста на 2–4 с [п. 2 `OWNER-ACTIONS.md`: soft lockup] даёт промахи
опроса, но люди за это время ещё не пожаловались (их SDK ждёт pong дольше), а если пожаловались половиной — медиа у них
и правда стоит ≥ 5 с, и переезд за 1 с лучше ожидания. Ложный переезд стоит 1–2 с тишины; пропущенная смерть — 10+ с.

### 5.3 Клиент: не ждать SDK

- По `room.changed` с ростом `mediaMoves` клиент **уже** переезжает немедленно (`relocate`, 1.2.1) — независимо от того,
  заметил ли SDK обрыв. Это остаётся главным путём: решение ядра → вход ≈ 1 с.
- `media.lost` клиент должен слать **раньше**: сегодня — когда SDK перешёл в `reconnecting` (9,4 с). Добавить сигнал
  «входящее молчание по STUN-счётчикам ≥ 3 с при `connected`» (`silence-watch.ts` уже считает — слать ядру отметку
  `media.stall`, без действий у клиента). Тогда признак A набирается за ≈ 4 с.
- Окно восстановления после переезда — как в 1.2.1 (сервер даёт свежие `recovery-seconds`).

### 5.4 Ожидание и приёмка

Цель: **≤ 8 с от остановки SFU до звука у всех** (5 прогонов, худший ≤ 10 с); ни одного переезда за сутки на живом B при
искусственных паузах магистрали (`docker pause backbone` на A на 15 с) и при `stress-ng --cpu 2` на B 10 с.

### 5.5 Чего не делаем

- Не снижаем `ping_timeout` SFU ради скорости: это ломает людей на плохом Wi-Fi (resume при каждом провале).
- Не переезжаем по одному жалобщику и не по метрикам мониторинга (VictoriaMetrics — не источник решений ядра).
- Не возвращаем комнаты на оживший узел (как в 1.2.1).
