# Админ-панель Cord и служба `fleet` (R207): проект

Статус: **проект, принят к разработке** — владелец (08.11.2026): «приступай к полноценной проектировке и разработке
админ панели». Схема серверов — Р-110/Р-110′ (`backlog/DECISIONS.md`): A (108.165.32.75, `callcord.ru`) — стенд
разработки и админ-панель `admin.callcord.ru`; продукт `cordcam.ru` — ядро на meet (108.165.32.23) + медиаузлы `fra`
(meet), `hel` (B, 152.234.227.199), `msk` (cordcam, 157.22.241.114). Решения этого проекта — Р-111…Р-120 (§12).

Слова владельца, из которых растёт проект: «все управление и админ панель будет теперь только на этом сервере, а
остальные будут служить рабочими машинами для проекта… нужно сформировать страницу админ панели тут. Где будет кнопка
тех работ, кнопки добавления сервера, кнопки управления, и много прочего для гибкого и большого управления системой»;
«так полагаю для админ панели нужно все данные и кубер и докер и все управление».

## 1. Зачем и что это

Один пульт, с которого владелец видит весь флот и управляет им кнопками — тем, что сегодня делается скриптами по SSH
(`backlog/bin/deploy.sh`, `node.sh`, `maintenance.sh`, `publish-windows.sh`, `active-meetings.sh`) и страницей
«Активность» на каждом сервере отдельно.

Три принципа:

1. **Панель ничего не умеет сама.** Каждая кнопка зовёт уже существующий рычаг — админ-API ядра продукта
   (`/api/v1/admin/*`) или скрипт из `backlog/bin` — пишет в журнал и показывает исход. Панель лежит — всё то же
   делается руками, как сейчас; ни один рычаг не живёт только в панели.
2. **Секреты продукта остаются на машинах продукта.** A хранит только свои: пароль пульта, секрет одноразового кода,
   ключ пульта к ядру и ключи SSH. Пароль владельца `cordcam.ru`, ключи SFU, база — не покидают meet.
3. **Опасное — за подтверждением, с дренажем и возможностью отката.** Выкатка ждёт конца встреч (как `deploy.sh`),
   удаление узла требует напечатать его имя, всё необратимое объявляет заранее, что произойдёт («сухой прогон»).

## 2. Пользователи и модель угроз

**Кто пользуется.**

| Кто | Как | Что может |
| --- | --- | --- |
| Владелец | браузер, `admin.callcord.ru`, пароль + одноразовый код | всё |
| Агент-сессия (Claude/GPT на A) | тот же API службы `fleet` по ключу агента с 127.0.0.1 (`FLEET_AGENT_KEY`) | читать всё; рычаги — только те, что владелец разрешил ключу (по умолчанию: чтение, окно работ, дренаж; выкатка — нет) |
| Никто другой | — | даже не узнаёт, что страница существует |

**Что защищаем.** Рычаги остановки продукта (окно работ, завершение встреч, выкатка, удаление узла); ключи SSH на A,
которыми можно стать root на машинах продукта; ключ пульта к ядру; журнал (в нём адреса людей и имена комнат).

**От чего.**

| Угроза | Чем закрыто |
| --- | --- |
| Подбор пароля по сети | второй фактор (TOTP), 5 попыток в минуту с адреса и 10 подряд → адрес заперт 15 минут; список разрешённых адресов (§4.2) — остальным 404 на уровне шлюза |
| Украденная кука | `__Host-`-кука, `HttpOnly`, `Secure`, `SameSite=Strict`; сессия 8 часов, не дольше часа бездействия; список сессий с кнопкой «выйти везде»; смена пароля гасит все сессии |
| CSRF из чужой вкладки | `SameSite=Strict` + заголовок `X-Fleet-Request: 1` обязателен на всех изменяющих запросах + проверка `Origin` = `https://admin.callcord.ru` |
| XSS | тот же CSP, что у приложения (`default-src 'self'`, встроенных скриптов нет); текст журналов и ответов машин — всегда текстом, никогда HTML |
| Инъекция команды через форму («добавить сервер», «выкатить ветку») | ввод превращается в `argv` по каталогу операций (§6.3): имя узла `[a-z][a-z0-9-]{1,15}`, ветка/коммит `[A-Za-z0-9._/-]`, служба — из перечня; оболочки (`sh -c`) с подстановкой ввода нет |
| Компрометация A | ключи SSH на A и так дают root на машинах продукта (это уже так с 08.11, их положил GPT) — панель риск не увеличивает, но и не уменьшает; снижение: отдельный пользователь `cord-fleet` на машинах с `sudo` только на `backlog/bin/*` (§6.4, решение владельца) |
| Паника ночью: нажал не то | подтверждения с описанием последствий; удаление/выкатка требуют напечатать имя узла; сухой прогон по умолчанию у новых операций; откат одной кнопкой на предыдущий коммит |
| Агент-сессия делает лишнее | ключ агента с явным перечнем разрешённых операций; каждый вызов в журнале с меткой `agent` |

Чего **не** защищаем: от владельца с паролем и кодом; от того, кто уже root на A.

```
   │    ├── CoreLink ──► ядро продукта на meet — туннель SSH или магистраль mTLS (§6.2) ─ ─ ─ ─│─ ─ ► meet
   │    ├── Executor ──► ssh -i /keys/cord_fra root@meet  backlog/bin/… (§6.3) ─ ─ ─ ─ ─ ─ ─ ─│─ ─ ► meet, cordcam, B
   │    ├── Metrics ───► VictoriaMetrics 127.0.0.1:8428, vmalert :8880 (профиль monitoring)    │
```

- **Фронт** — третий HTML-вход веба `web/admin.html` → `web/src/admin/` (как `tg.html` для Mini App): тот же набор
  `ui/kit`, те же токены `styles/tokens.css`, та же сборка. Шлюз отдаёт его **только** на имени `ADMIN_HOST`
  (`infra/Caddyfile`, блок `@admin`); имя пусто — блок привязан к `admin.invalid` и недостижим, продукт на meet его не
  показывает вовсе. На A `ADMIN_HOST=admin.callcord.ru` (`scripts/configure.mjs --admin=…`).
- **Служба `fleet`** — `services/fleet/` (Python 3.12, FastAPI, как `services/cord_services`), свой лёгкий образ
  (`services/fleet/Dockerfile`: python-slim + `openssh-client`; ни ffmpeg, ни yt-dlp), `network_mode: host`, слушает
  `127.0.0.1:18200`, профиль compose `admin` — в продукте не поднимается. Состояние — SQLite в томе `fleet-data`.
  Настройки — `.local/fleet.env` (0600, root), **не** `.env`: продукту секреты пульта незачем, пульту — секреты продукта.
- **Ядро продукта** получает один новый вход — ключ пульта `FLEET_KEY` (§6.2); остальное — существующий админ-API.

### 3.1. Kubernetes или Docker Compose (Р-111, обоснование)

Владелец спросил про «кубер». Ответ — **не сейчас**, и вот почему в цифрах:

| Критерий | Kubernetes (k3s) на наших VPS | Compose + реестр + пульт (сейчас) |
| --- | --- | --- |
| Сеть кластера | flannel VXLAN/WireGuard/Cilium — UDP между узлами; **UDP между нашими VPS режется** (замер 07.11.2026, поэтому магистраль — mTLS по TCP) → нужен host-gw с маршрутами или TCP-туннели, то есть нестандартная сборка | магистраль mTLS/TCP уже работает |
| Цена на узле 2 vCPU/4 ГБ (`msk`) | k3s agent ≈ 0,7–1 ГБ RSS и ≈ 10 % ЦП в простое — у SFU это треть памяти машины | ≈ 0 сверх контейнеров |
| Обновление без обрыва звука | rolling update убивает под SFU по таймауту — живые встречи рвутся; нужен свой контроллер дренажа | дренаж через реестр (`--enabled=false` → ядро не ставит новые встречи, идущие доигрывают) уже сделан |
| SFU и сеть | один SFU на машину с `hostNetwork`, TURN на 443/3478 — поды с host-сетью, то есть k8s как «докер с планировщиком» | то же без планировщика |
| Что даёт k8s, чего нет у нас | декларативное желаемое состояние, самолечение, единый API | реестр узлов — тот же декларативный файл; самолечение — `restart: unless-stopped` + алерты; единый API — это и есть `fleet` |
| Операторов | один владелец + агент; k8s требует держать в голове ещё один слой (etcd, CNI, сертификаты) | уже знакомо |

**Когда k8s станет оправдан:** ≥ 6–8 машин продукта **или** выделенные серверы с частной сетью без фильтра UDP
**или** второй оператор, который k8s знает лучше, чем Compose **или** появятся сервисы, которым нужен планировщик
(несколько реплик ядра, воркеры записи). Тогда — k3s с `hostNetwork` для SFU и свой контроллер дренажа; реестр узлов и
`fleet` переживут переход как есть, потому что они описывают «что», а не «как запустить».

До этого **Docker на каждой машине + реестр узлов + пульт** — ровно столько управления, сколько у флота из четырёх машин
есть смысла иметь. Все данные «и кубер и докер» пульт показывает и так: контейнеры, их здоровье и версии — через
`docker compose ps --format json` по SSH (операция `status`).

## 4. Вход, сессия, адреса

### 4.1. Пароль + одноразовый код (Р-113)

Cloudflare Access недоступен (записи серые, Р-109). Клиентский сертификат — надёжнее, но ставить его на каждый телефон и
ноутбук владельца и поддерживать выпуск — отдельная работа; оставлен **вариантом второго этапа** (§4.4).

Сейчас: **пароль пульта + код TOTP (RFC 6238, 30 с, 6 цифр, окно ±1 шаг)**. Пароль хранится как `scrypt` (stdlib,
`n=2^15, r=8, p=1`, соль 16 байт) в `FLEET_PASSWORD_HASH`; секрет кода — `FLEET_TOTP_SECRET` (base32, 20 байт). Оба —
в `.local/fleet.env`; выпуск — `node scripts/fleet-setup.mjs` печатает QR-код для приложения-аутентификатора в терминал
(ASCII) и пишет файл; повторный запуск меняет пароль/секрет и гасит все сессии. Один аккаунт — владелец; второго не
предусмотрено (нет учётных записей в Cord — Р-… «владелец — тот, кто знает пароль»).

Ошибка входа одна для всех причин («Неверный пароль или код») — не говорим, что именно не так. Попытки: 5 в минуту с
адреса, 10 неверных подряд с адреса → адрес заперт на 15 минут (в журнал — `auth.locked`).

### 4.2. Список разрешённых адресов

`FLEET_ALLOW_IPS` — CIDR через запятую; пусто — любые (тогда защита — только §4.1). Проверяет служба по `X-Real-IP`
от шлюза; чужому адресу — `404` без тела, тем же ответом, что у несуществующей страницы. Рекомендация владельцу: домашний
и мобильный диапазоны; при смене адреса вход открывается с A по SSH (`scripts/fleet-setup.mjs --allow=…`).

### 4.3. Сессия

Кука `__Host-fleet` (`HttpOnly; Secure; SameSite=Strict; Path=/`), значение — 32 случайных байта, хранится хэшем в
SQLite (`sessions`: id, hash, создана, последняя активность, адрес, user-agent). Живёт 8 часов от входа и не дольше 60
минут без запросов; продление — каждым запросом. Экран «Сессии» в разделе «Журнал» — выйти из одной или всех. Выход —
удаление строки. Смена пароля (§4.1) — `DELETE FROM sessions`.

Изменяющие запросы (`POST/PUT/DELETE`) обязаны нести `X-Fleet-Request: 1` и `Origin`, равный `https://ADMIN_HOST`;
иначе `403`. Ключ агента (`X-Fleet-Agent`) — только с 127.0.0.1 (без `X-Real-IP` от шлюза), без куки и без CSRF.

### 4.4. Второй этап (не сейчас)

- Клиентский сертификат на edge (`caddyl4` → `tls client_auth`) для имени `admin.callcord.ru` — тогда §4.1 остаётся
  вторым слоем. Нужно решение владельца: он выпускает и ставит сертификаты на свои устройства.
- WebAuthn/пасскей вместо TOTP — когда появится второй пользователь.

## 5. Журнал (аудит) пульта

Каждое действие пульта — строка `audit` в SQLite A (только добавление, никакого UPDATE/DELETE из кода):

```
ts, actor ('owner'|'agent'), session_id, ip, action, target (машина/узел/комната), args (json, без секретов),
outcome ('ok'|'refused'|'failed'), detail (текст ≤ 2 КБ), job_id
```

Что пишется: вход (удачный/неудачный/запертый адрес), выход, каждый рычаг (с аргументами), каждая задача (старт,
финал, исход), смена настроек пульта, экспорт журнала. Чтение (просмотр экранов) **не** пишется — иначе журнал тонет.

Рычаги ядра продукта пишутся и в аудит ядра (там actor `admin`, как у страницы «Активность»): панель показывает оба
журнала рядом — свой и ядра (`GET /api/v1/admin/audit`) — на экране «Журнал» двумя вкладками. Экспорт — JSONL за
период. Хранение — 400 дней (как у ядра), чистка — раз в сутки при старте службы.

## 6. Служба `fleet`

### 6.1. Модель данных

- **Machine** — машина флота: `id` (`a`, `meet`, `cordcam`, `b`), `role` (`dev+admin`, `product-core`, `media-node`),
  `host`, `ssh` (`root@ip`), `sshKey` (путь внутри контейнера), `installDir` (`/opt/ModernStreamingSystem`,
  `/opt/meet/ModernStreamingSystem`, `/opt/cord/node`), `nodeId` (если это медиаузел), `core` (`url`, `credential`).
  Источник — `FLEET_MACHINES` (json в `.local/fleet.env` или файл `/data/machines.json`, редактируется экраном
  «Узлы → Машины»). Кто чем управляет: медиаузлы продукта правятся **через meet** (`node.sh` там, где реестр продукта).
- **Job** — задача: `id`, `kind` (из каталога §6.3), `machine`, `args`, `actor`, `dry_run`, `status`
  (`queued|running|ok|failed|cancelled`), `started_at`, `finished_at`, `exit_code`, строки вывода `job_lines(job_id, n,
  ts, stream, text)`. Одна задача на машину одновременно (блокировка в SQLite); параллельно на разных — можно.
- **Session**, **Audit** — §4.3, §5.
- **Settings** — флаги пульта (`executor=dry-run|ssh`, подтверждение «вживую»).

### 6.2. Связь с ядром продукта (Р-115)

Ядро получает **ключ пульта** `FLEET_KEY` (`.env` meet): токен `X-Cord-Admin: fleet.<ключ>` принимается
`AdminAccess.valid` наравне с сессией владельца — без изменений контроллеров и контрактов. Сравнение — постоянное по
времени; ключ ≥ 32 байт из `openssl rand`. Пароль владельца `ADMIN_PASSWORD` панели не нужен и на A не хранится.

Канал A → ядро meet (ядро слушает `127.0.0.1:8080`, снаружи — только через шлюз cordcam.ru):

| Вариант | Как | Плюсы | Минусы |
| --- | --- | --- | --- |
| **Туннель SSH** (первый) | `ssh -N -L 127.0.0.1:28080:127.0.0.1:8080 meet` тем же ключом, что для команд; `CoreLink` ходит на `127.0.0.1:28080` | ничего нового на meet, ключ уже есть, обрыв — переподключение | ещё один процесс; привязан к SSH |
| Магистраль mTLS (второй) | A — «узел-пульт» в `node-config.mjs` meet: `backbone.json` meet принимает сертификат A и отдаёт `8080` | штатная магистраль, метрики и ядро по одному каналу | правка `backbone-config.mjs`, выпуск сертификата A на meet, 7443 открыть с A |
| Публичный `https://cordcam.ru/api/v1/admin` | ключ в заголовке через шлюз | ничего не нужно | ключ пульта идёт через публичный вход; `fleet.`-токен снаружи — лишняя поверхность → **нет** |

Стенд A — `http://127.0.0.1:8080` со своим `ADMIN_PASSWORD` стенда (это секрет A, не продукта) — работает уже сейчас и
служит для разработки и проверки.

### 6.3. Исполнитель команд (Executor, Р-116)

Интерфейс один: `Executor.run(machine, operation, args) → Job`. Операции — **каталог**, не свободная строка:

| `kind` | argv на машине (`cwd = installDir`) | Предусловия | Отменяемо |
| --- | --- | --- | --- |
| `status` | `docker compose ps --format json`; `git rev-parse --short HEAD`; `uptime -p`; `df -h /` | — | — |
| `logs` | `docker compose logs --tail {n} {service}` | `service` из перечня, `n ≤ 500` | — |
| `active-meetings` | `backlog/bin/active-meetings.sh [--node id]` | — | — |
| `maintenance.*` | **не** скрипт — `CoreLink` (API окна работ R194) | — | — |
| `deploy` | `backlog/bin/deploy.sh [--drain] {services…}` | нет встреч или `--drain`; `CORD_DEPLOY_FORCE` — только с подтверждением «люди не идут» | да (SIGINT → trap снимает обслуживание) |
| `rollback` | `git checkout {commit} && backlog/bin/deploy.sh --drain {services…}` | `commit` из истории выкаток пульта | да |
| `node.check` / `node.logs` | `backlog/bin/node.sh {id} check|logs` | узел в реестре машины | — |
| `node.drain` / `node.undrain` | `node scripts/node-config.mjs --node={id} --enabled=false|true` | — | — |
| `node.deploy` | `backlog/bin/node.sh {id} deploy` | узел дренирован и `active-meetings --node {id}` пуст | да |
| `node.update` | `drain → ждать конца встреч (≤ 15 мин) → node.deploy → check → undrain` | — | да |
| `node.add` | `node scripts/node-config.mjs --node=… --ip=… …` затем `node.sh {id} bootstrap` и `deploy` | форма §8.3 проверена; DNS-записи подтверждены владельцем | да |
| `node.remove` | `node scripts/node-config.mjs --node={id} --remove` (добавить в генератор) | узел дренирован, встреч нет, имя напечатано | нет |
| `publish-windows` | `backlog/bin/publish-windows.sh {version}` | — | — |

Три реализации:

- `DryRunExecutor` — **по умолчанию**: не подключается никуда, печатает в задачу точный `argv`, предусловия и то, что
  произойдёт; задача завершается `ok` с пометкой `dry_run`. Это же — кнопка «Сухой прогон» у любой операции.
- `FakeExecutor` — для тестов: сценарии вывода и кодов выхода.
- `SshExecutor` — `ssh -o BatchMode=yes -o ConnectTimeout=15 -i {sshKey} {ssh} -- {argv}`; stdout/stderr построчно в
  `job_lines`, SIGINT по отмене, таймаут операции (`deploy` — 40 мин, остальные — 5). **Выключен**, пока владелец не
  разрешит: включается `FLEET_EXECUTOR=ssh` **и** списком машин `FLEET_SSH_MACHINES=meet,cordcam,b`; без обоих —
  `409 EXECUTOR_DISABLED` с объяснением. Ключи — том `/keys` только для чтения.

Что ввод превращается в `argv` без оболочки, проверяется тестами на каждую операцию (`test_catalog.py`).

кнопкой «Повторить», данные прошлого обновления остаются на экране с пометкой «на HH:MM»; **опасное подтверждение** —
`Dialog` с заголовком-глаголом, перечнем последствий, полем для имени (для удаления/выкатки вживую) и красной кнопкой;
**сухой прогон** — те же диалоги, но кнопка «Показать план» вместо красной.

Локализация: **только русский** (Р-114): пульт — для владельца, тексты — `web/src/i18n/admin/ru.ts`; в каталог
`locales/*.json` не входят и восьми переводов не требуют; храповик кириллицы (`scripts/i18n/check.mjs`) каталог `i18n/`
не считает. Если появится второй оператор с другим языком — переносится в каталог обычным путём.

### 8.3. Добавить сервер (форма → план)

Поля: `id` (`[a-z][a-z0-9-]{1,15}`, не занят), IP (v4), страна (ISO-2, флаг из `kit/Flag`), названия ru/en, домены
(`<id>.cordcam.ru`, `rtc-<id>`, `turn-<id>` — подставляются, можно править), ёмкость (`maxRooms`, `uplinkMbps`,
`cores`), SSH (`root@ip`, ключ из списка `/keys`). Кнопка **«Составить план»** → справа план:

```

                                               rtc-msk.cordcam.ru  A 157.22.241.114

   node scripts/node-config.mjs --control-id=fra --write-env   # CSP, профиль nodes
```

зелёная/красная строка с кодом выхода.

### 8.8. Метрики и журналы

По машине — четыре ряда за 5 мин (VictoriaMetrics instant): ЦП `1-avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))`,

Метки машин — `instance`/`job` из `scrape.yml` и `scrape-nodes/*.json`. Ссылки «Открыть в Grafana» ведут на
`http://127.0.0.1:3000` через туннель SSH (как сегодня) — Grafana за пульт не выставляется. «Хвост журнала» — операция
`logs` (служба из перечня, 100/500 строк) → экран задачи. Нет профиля `monitoring` — плашки говорят об этом, не падают.

## 10. Предохранители

1. **Дренаж перед выкаткой** — по умолчанию включён; `deploy.sh` сам не выкатит при встречах без `--drain`/force —
   пульт эту проверку не обходит, а показывает.
2. **`active-meetings`** — перед `node.deploy`, `node.remove`, окном «сейчас» пульт показывает число встреч и людей на
   машине/узле; при ненулевом — красная пометка в диалоге.
3. **Подтверждения** — все изменяющие действия; разрушительные (удалить узел, выкатка вживую с force) — имя машины/узла
   вручную.
4. **Сухой прогон** — у каждой операции; исполнитель `dry-run` по умолчанию для всей службы.
5. **Откат** — история выкаток с коммитами; `rollback` — тот же `deploy.sh --drain` на прежний коммит.
6. **Одна задача на машину** — вторая ждёт в очереди или отказывается (`409 MACHINE_BUSY`).
7. **Таймауты и отмена** — у каждой операции, отмена шлёт SIGINT, `deploy.sh` снимает обслуживание по `trap`.
8. **Ключ агента ограничен** — перечень операций в `FLEET_AGENT_OPS` (по умолчанию `read,maintenance,drain`).
9. **Никаких секретов в журнале** — аргументы операций проверяются каталогом; переменные окружения в задачах не
   печатаются; `env-flags` читает только `*_ENABLED`.
10. **Панель без прав — ничего не ломает**: исполнитель выключен → каждая кнопка показывает план и пишет в журнал.

## 12. Решения (Р-111…Р-120)

- **Р-111 (предложение → принято проектом): без Kubernetes** — §3.1; пересмотр при ≥ 6–8 машинах, частной сети без
  фильтра UDP или втором операторе.
- **Р-112. Служба `fleet` — Python/FastAPI в `services/fleet/`, свой лёгкий образ, профиль compose `admin`,
  SQLite.** Тот же стек, что у `services/`; SSH и TOTP — stdlib; продукт её не поднимает.
- **Р-113. Вход — пароль (scrypt) + TOTP; кука `__Host-fleet`, 8 ч / 60 мин бездействия; allowlist адресов; CSRF —
  `SameSite=Strict` + заголовок + `Origin`.** Клиентский сертификат — второй этап (B16), по решению владельца.
- **Р-114. Пульт — только по-русски**, тексты в `web/src/i18n/admin/ru.ts`, вне каталога восьми языков.
- **Р-115. Ключ пульта `FLEET_KEY` в ядре: токен `fleet.<ключ>` в `X-Cord-Admin`.** Пароль владельца продукта на A не
  хранится. Канал к ядру meet — туннель SSH (первый), магистраль mTLS (второй); публичный вход — нет.
- **Р-116. Исполнитель — каталог операций → `argv`, без оболочки; `dry-run` по умолчанию; `ssh` — только с
  `FLEET_EXECUTOR=ssh` и `FLEET_SSH_MACHINES`.** Выключен до явного разрешения владельца.
- **Р-117. Задачи — строки в SQLite, вывод построчно, опрос `after=N`; одна задача на машину.** Без SSE/WebSocket:
  опрос раз в секунду проще и переживает обрыв.
- **Р-118. Журнал пульта — только добавление, 400 дней, рядом с журналом ядра; чтение не пишется.**
- **Р-119. Фронт — третий HTML-вход `admin.html` в бандле веба, отдаётся шлюзом только на `ADMIN_HOST`; пусто → имя
  `admin.invalid`.** Тот же CSP и набор `ui/kit`.
- **Р-120. Секреты пульта — `.local/fleet.env` (0600), не `.env`; ключи SSH — том `/keys:ro`.** Где именно они лежат
  (на A в `/root/.ssh` или отдельный каталог) — решение владельца.
