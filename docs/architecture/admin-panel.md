## 3. «Кубер и докер»: честная оценка

### 3.1 Что у нас есть и какие ограничения

- 3–4 VDS: A 4 vCPU/7 ГБ, B 2 vCPU/3,8 ГБ, meet и cordcam — характеристики ждём от GPT (`rollout-cordcam.md` «Сейчас»
  п. 1); по T09 и `docs/capacity.md` узел на 2 vCPU держит 2 встречи, обслуживать его должна **одна** машина.
- **UDP между A и B фильтруется** на стороне хостера A (`distributed-media.md` §1, замер 07.11: STUN B→A доходит, A→B — нет);
  поэтому магистраль — mTLS по **TCP** (`caddy-l4`), и медиа между узлами не ходит вовсе.
- SFU: один процесс LiveKit на машину, `network_mode: host`, UDP 7882 + TCP 7881 + TURN 3478/443, `node_ip` в конфиге.
- Один оператор (владелец) и агент-сессия. Выкатка — только без встреч на машине (правило №2 `CLAUDE.md`).

### 3.2 Сравнение по критериям

| Критерий | k3s / Kubernetes на этих VDS | Docker Compose на каждой машине + реестр + пульт на A (сегодня + панель) |
|---|---|---|
| **Сеть кластера** | Сеть подов по умолчанию — flannel VXLAN (UDP 8472), альтернативы — WireGuard (UDP 51820), Cilium VXLAN/Geneve (UDP) [источник 1, 2]. Между A и другими VDS UDP режется → под-сеть **не поднимется** без обходов: `host-gw` требует общего L2 (у VDS нет), Tailscale-интеграция k3s ходит через DERP по TCP только как запасной путь с задержкой [источник 3]. Выход — всё с `hostNetwork` и без под-сети, то есть k8s как планировщик без сети. | Под-сети нет и не нужно: службы одной машины — на её 127.0.0.1, между машинами — mTLS TCP 7443 по SNI. Работает [измерено R195]. |
| **SFU** | DaemonSet с `hostNetwork: true`, `node_ip` из Downward API, UDP-диапазон открыт на хосте; это штатно (LiveKit так и ставят в k8s [источник 4]), но ничего не даёт сверх `compose`: один SFU на машину, масштабирования «подами» нет. | `compose.node.yaml`: `livekit` в `network_mode: host`. |
| **Обновление без обрыва встреч** | Rolling update убивает под по `terminationGracePeriod`; чтобы не рвать встречи — `preStop`, который ждёт конца комнат (до часов) — k8s это терпит плохо (дедлайн дренажа узла), придётся писать свой оператор. | Уже есть: `enabled:false` в реестре → новых встреч нет → `active-meetings.sh --node` → `node.sh deploy`. Панель это оборачивает кнопкой «Дренаж → Выкатить». |
| **Отказоустойчивость** | k3s с одним server — единая точка отказа **плюс** к нашей (ядро); HA — три server с etcd на A, meet и B через TCP-магистраль (etcd на 20–40 мс RTT работает, но при обрыве магистрали кворум 2 из 3 решает, кто живой — и может снять поды с живого узла). Для встреч это **хуже**: сегодня узел без связи с ядром продолжает держать идущие встречи (R195 §5.3). | Отказ узла: ядро замечает по `ListRooms` (8.5 — за ≈ 6–8 с), переселяет комнаты. Отказ A: продукт не замечает ничего (пульт — не часть пути звонка). Отказ meet: продукт лежит — как и в k8s без HA-ядра; HA ядра — отдельный вопрос (R195 фаза 4, standby Postgres). |
| **Накладные расходы** | k3s server ≈ 0,5–1 ГБ RAM и 5–15 % ЦП в простое, agent ≈ 0,2–0,4 ГБ [источник 5, оценка на 2 vCPU]; на B это 10–25 % памяти и ЦП, которых и так не хватает SFU (steal до 50 % по T09). | Docker + compose: ≈ 100 МБ. |
| **Сложность для одного оператора** | Вторая система понятий (манифесты, Helm/Kustomize, RBAC, CNI, Ingress, PV), своя ломкость при обновлениях k3s; отладка «почему под не стартует» вместо `docker compose logs`. | Одна система: compose-файлы в репе, `.env`, три скрипта. Панель делает их кнопками. |
| **Секреты и конфиги** | Secrets/ConfigMaps — удобно, но раздача ЦС, TURN-сертификатов и `node.env` у нас уже решена rsync по SSH (R195 §5.8). | Как есть. |
| **Наблюдаемость** | kube-state-metrics, события — лишний слой. | VictoriaMetrics + node-exporter + метрики LiveKit/ядра — есть. |
| **Что k8s дал бы реально** | Декларативное «желаемое состояние» и перезапуск упавшего (compose `restart: unless-stopped` делает то же), bin-packing многих мелких служб (у нас служб 5–6 и они привязаны к машинам), автоскейл (SFU не масштабируется подами). | — |

### 3.3 Вывод и рекомендация

**Не вводить Kubernetes сейчас.** Он не помещается в сеть (UDP), не экономит ресурсы на 2-vCPU узлах, а главный его
аргумент — rolling update — для живых встреч нам как раз противопоказан. Рекомендация: **Docker Compose на каждой машине
как сейчас + реестр узлов (есть) + служба `fleet` на A**, которая выполняет те же шаги, что сегодня делает человек
(`deploy.sh`, `node.sh`, `maintenance.sh`), по SSH и по магистрали, пишет журнал задач и показывает состояние. Это ровно
«докер и всё управление» из слов владельца, без «кубера».

### 3.4 Когда Kubernetes станет оправдан

Любые **два** из условий:

1. **≥ 6–8 машин** одного рода (узлы), или появляются stateless-службы, которые нужно размножать по нагрузке (транскодеры
   записи, боты, кинозал на несколько экземпляров).
2. **Выделенные серверы или облако с частной сетью** (один хостер, VPC/L2 между машинами, UDP не режется) — тогда
   CNI работает штатно и etcd живёт в одной стойке.
3. **Второй оператор/команда**, для которых декларативные манифесты важнее знания трёх скриптов.
4. Нужда в **HA плоскости управления** (несколько экземпляров ядра за балансировщиком, Postgres HA) — k8s не делает HA
   базы сам, но упорядочивает остальное.

До этого — compose. Решение зафиксировать как **Р-111** (предложение; владелец подтверждает).

## 4. Архитектура пульта

### 4.1 Части

| Часть | Где | Что это | Технология |
|---|---|---|---|
| **Панель** (UI) | A, `admin.callcord.ru` | отдельный HTML-вход веба `admin.html` (как `tg.html`), SPA из того же `web/` с тем же набором компонентов (`kit`), доступен только на этом имени | React, та же сборка |
| **`fleet`** (служба пульта) | A, контейнер в `compose.yaml` профиль `fleet` | каталог машин, выполнение задач (SSH), прокси к админ-API продукта по магистрали, журнал аудита пульта, флаги, выпуски | Java (Spring Boot, модуль `fleet` рядом с `server` — те же инструменты, тесты, CI) **или** Go (как `publisher`); рекомендация — **Java**: переиспользуем `Audit`, `Problem`, `Secrets`, i18n ошибок, контракты OpenAPI → `generated.ts` |
| **Магистраль-пульт** | A ↔ meet | A как клиент ЦС продукта: `fleet.cord` сертификат, маршрут `127.0.0.1:27000 → meet:7443` с SNI `core.fra.cord` | `backbone-config.mjs`: новая роль `fleet` |
| **Админ-API продукта** | meet, ядро | то, что есть (`/api/v1/admin/*`, `/admin/maintenance/window`, `/admin/support`), плюс **дверь пульта**: заголовок `X-Fleet-Key` (= `FLEET_SECRET`), принимается только с 127.0.0.1 (пришло по магистрали) | `AdminAccess` получает вторую проверку |
| **SSH-исполнитель** | A → каждая машина | `node.sh`, `deploy.sh`, `publish-windows.sh` на удалённой машине; поток вывода в панель (SSE) | ключи `/root/.ssh/cord_<id>` (есть для B) |
| **Мониторинг** | A | VictoriaMetrics scrape всех машин по магистрали (`scrape-nodes/*.json` — есть для узлов; добавить `core`/`gateway`/`services` meet), Grafana, vmalert, Gatus снаружи | как сегодня, переезжает с прода на A |

### 4.2 Поток «кнопка → действие»

```
владелец → панель (HTTPS, Access/mTLS, пароль+TOTP) → fleet (A)
   чтение:   fleet → 127.0.0.1:27000 ──mTLS──► meet:7443 ──► 127.0.0.1:8080 /api/v1/admin/*  (X-Fleet-Key)
   рычаг:    то же (закрыть встречу, блок, окно работ, дренаж, флаг)              → audit_events ядра + журнал пульта
   выкатка:  fleet → ssh -i cord_fra root@meet 'cd /opt/cord && git fetch && backlog/bin/deploy.sh --drain core gateway'
             fleet → ssh -i cord_hel root@B    (через node.sh на meet? — нет: node.sh нужен .env продукта → см. 4.3)
```

### 4.3 Где выполняются `node-config.mjs` и `node.sh`

Они читают `.env` продукта и пишут реестр и ЦС — это **meet**. Два варианта:

| | (а) `fleet` зовёт их **на meet** по SSH (`ssh meet 'node scripts/node-config.mjs …; backlog/bin/node.sh hel deploy'`), а meet ходит к узлам своими ключами | (б) Перенести реестр и ЦС на A, meet читает реестр с A |
|---|---|---|
| Плюсы | ничего не меняется в R195: узел управления сам раздаёт секреты; у A нет секретов продукта | «всё управление на A» буквально |
| Минусы | A → meet → узел: два прыжка SSH; на meet нужны ключи к узлам (они и так нужны ядру? нет — ядро ходит по магистрали; ключи нужны только `node.sh`) | ядро продукта зависит от A при каждом перечитывании реестра; секреты продукта (`LIVEKIT_API_SECRET`, `INTERNAL_SECRET`) оказываются на A — против R195 §5.8 |
| Решение | **(а)**. A держит ключ к meet; ключи к узлам лежат на meet (`/root/.ssh/cord_<узел>`), `node.sh` там же. Панель показывает вывод как одну задачу. | — |

### 4.4 Что делает `fleet` сам, а что — ядро продукта

| Задача | Кто | Почему |
|---|---|---|
| Встречи сейчас, закрыть встречу, блокировки, «щит», обращения, ошибки клиентов, журнал аудита продукта | ядро продукта (есть) | данные там; пульт — тонкий прокси с подменой двери |
| Окно работ, дренаж | ядро продукта (есть: `MaintenanceController`, `/admin/maintenance`) | то же |
| Узлы: список, ступени, живость, дренаж узла (`enabled`) | ядро продукта (`GET /api/v1/nodes` — есть; `PUT /admin/nodes/{id}` — **новое**: правит `enabled` в реестре на meet без `node-config.mjs`) | реестр у ядра |
| Добавить сервер (имя, IP, страна, канал, ядра, maxRooms) | `fleet` → SSH на meet: `node-config.mjs --node=… --country=… --uplink-mbps=…` → `node.sh <id> bootstrap && deploy`; владелец параллельно делает DNS (панель показывает, какие записи ждать, и проверяет `dig`) | нужны файлы на meet |
| Выкатить / откатить машину | `fleet` → SSH: meet — `deploy.sh [--drain] <службы>`; узел — `node.sh <id> deploy`; откат — `deploy.sh` по тегу `cord-rollback-*` (теги уже делает `rollout.md` §4.2; оформить в `deploy.sh --rollback <тег>`) | только SSH умеет пересобирать и перезапускать |
| Флаги возможностей | ядро продукта: **новая** таблица `feature_flags` + `GET /capabilities.flags` + `PUT /admin/flags/{name}` | клиенты уже читают `capabilities`; флаг действует без перезапуска |
| Выпуски клиента | `fleet`: читает GitHub Releases/Actions (`gh api`, токен владельца — **на A, не на проде**), по кнопке — SSH на meet `publish-windows.sh X.Y.Z`; каталог серверов — показать текущий `servers.jws`, предложить новый `servers.source.json`, **подпись — у владельца** (ключ не на серверах, ADR 0001 §8) | ключи остаются где были |
| Метрики и графики | VictoriaMetrics на A (PromQL через `fleet`, не напрямую) | один источник правды, уже есть панели Grafana |
| Журналы | фаза A — `docker compose logs --tail N` по SSH по кнопке (с фильтром службы); фаза C — Vector на каждой машине → VictoriaLogs на A по магистрали (TCP) | без нового софта в фазе A |

## 5. Безопасность

1. **Только A, только одно имя.** `admin.callcord.ru` → A; на `cordcam.ru`/узлах админ-путей нет: `ADMIN_PASSWORD` на
   проде **пуст** → `/activity` и `/api/v1/admin/*` отвечают 404 владельцу-человеку [код `AdminAccess.requireEnabled`], а
   дверь пульта принимает **только** `X-Fleet-Key` и **только** с 127.0.0.1 (магистраль заканчивается на loopback meet).
   Снаружи до неё не дойти: публичный шлюз meet режет `/api/v1/admin/*` без заголовка так же, как сегодня (401/404).
2. **Три двери подряд на A** (любая одна не достаточна):
   - сетевая: **Cloudflare Access** на `admin.callcord.ru` (оранжевое облако допустимо — HTTP без медиа), политика «только
     e-mail владельца», код на почту или GitHub; A принимает запросы к этому имени **только** с адресов Cloudflare и с
     проверкой `Cf-Access-Jwt-Assertion` [источник 6] — **или**, если владелец не хочет Cloudflare, клиентский сертификат
     (Caddy `client_auth require_and_verify`, сертификат — в браузер/ОС владельца) — выбор владельца (п. §10);
   - приложение: пароль пульта (`FLEET_ADMIN_PASSWORD`, в `.env` A) **+ TOTP** (секрет один раз показывается QR при
     первом входе и хранится в `.env`/базе A; без TOTP вход невозможен);
   - сессия: токен на 8 часов (как `AdminAccess`), смена пароля отзывает все токены.
3. **Секреты.** На A — `FLEET_SECRET` (к ядру продукта), SSH-ключи к машинам, токен GitHub владельца (только чтение +
   выпуски). На A **нет** `.env` продукта, базы продукта, ключа каталога, ключа подписи обновлений. Ключи — `0600`,
   каталог `.local/fleet/`.
4. **Аудит каждого действия**: таблица `fleet_audit` на A — кто (владелец/агент), что, на какой машине, аргументы, начало,
   конец, исход, первые 64 КБ вывода; действия над продуктом ядро пишет ещё и в свой `audit_events` с `actor=fleet`.
   Вкладка «Журнал» объединяет оба.
5. **Опасные действия — подтверждение словом**: откат, удаление сервера, завершение встречи с людьми, окно работ «сейчас»
   требуют ввести имя машины/код встречи. Выкатка на машину с идущими встречами — только через «Дренаж → ждать →
   выкатить», кнопки «выкатить сейчас при людях» нет (правило №2 `CLAUDE.md` становится правилом интерфейса).
6. **Пределы частоты** на вход (как `AdminAccess`), на SSH-задачи — одна задача на машину одновременно (замок, как
   `backlog/.deploy.lock`).

## 7. Как добавляется сервер и как выкатывается флот (вместо GPT)

**Добавить сервер** (форма: id `msk`, IP, страна `RU`, город ru/en, канал Мбит/с, ядра, `maxRooms`, SSH-пользователь):

1. `fleet` проверяет SSH с meet на новую машину (ключ владелец положил на meet; панель говорит, какой именно).
2. `fleet` → SSH meet: `node scripts/node-config.mjs --node=msk --ip=… --app=msk.cordcam.ru --rtc=rtc-msk.cordcam.ru
   --turn=turn-msk.cordcam.ru --country=RU --title-ru=Москва --title-en=Moscow --uplink-mbps=… --cores=… --max-rooms=…
   --ssh=root@… --ssh-key=/root/.ssh/cord_msk` (флаги 8.1 — есть).
3. Панель показывает три DNS-записи, которые должен добавить владелец, и ждёт их (`dig` с A раз в 30 с).
4. `node.sh msk bootstrap` → `node.sh msk deploy` → `node.sh msk check` → `turn-relay-check.mjs` — одна задача, вывод в
   панель; на meet `ufw allow from <ip> … 7443` и `docker compose up -d backbone` (как `rollout.md` §7).
5. Узел появляется в `/api/v1/nodes` → в панели и у людей в настройках.

**Выкатить продукт** (meet): задача `deploy --drain core gateway services` = `ssh meet 'git fetch && git checkout <коммит>
&& backlog/bin/deploy.sh --drain …'`; перед этим панель показывает, зелёный ли CI на этом коммите (GitHub), и сколько
встреч идёт. **Откат**: `deploy.sh --rollback <тег>` (новый режим: `docker tag` обратно + `up -d --no-deps`).

**Выкатить узел**: «Дренаж» (`enabled:false` через `/admin/nodes/{id}`) → ждать `active-meetings --node` = 0 (панель
считает) → `node.sh <id> deploy` → `check` → «Снять дренаж». Все четыре шага — одна кнопка «Обновить узел» с паузой
ожидания, которую можно прервать.

**Dev-стенд A**: те же задачи локально (без SSH).

## 9. План и оценка

| Фаза | Что | Оценка |
|---|---|---|
| **A — пульт как есть** | `fleet` с входом (пароль+TOTP, Access/mTLS), каталог машин, прокси к админ-API продукта (вкладки Встречи, Тех. работы, Блокировки, Ошибки, Обращения — перенос `ui/activity`), Узлы (чтение + дренаж), задачи SSH (выкатка/откат/проверка узла) с журналом, `fleet_audit`, мониторинг на A | ≈ 30–35 ч |
| **B — управление флотом** | «Добавить сервер» формой, «Обновить узел» одной кнопкой, флаги возможностей, выпуски клиента (Windows на зеркало, APK, каталог), `deploy.sh --rollback`, статус CI в панели | ≈ 20 ч |
| **C — по желанию** | VictoriaLogs + Vector, графики в панели (сейчас — ссылки в Grafana), второй оператор с ролью «только чтение» | ≈ 12 ч |

Порядок относительно R200: сначала закончить 8.5 (отказ узла быстрее — независимо от топологии), затем фаза A пульта;
8.4 (тёплый переезд) — после, когда есть стенд с двумя SFU и пульт для него.

Приёмка фазы A: с ноутбука владельца через `admin.callcord.ru` — видно встречи продукта, узлы со ступенями, нажатие
«Тех. работы → Сейчас» включает страницу работ на `cordcam.ru` за ≤ 5 с и пишет две записи аудита; «Выкатить узел hel»
проходит дренаж → deploy → check с живым выводом; без Access/сертификата и без TOTP страница не открывается; на
`cordcam.ru` `/activity` отвечает 404.

## 10. Что решить владельцу

1. **Дверь на панель**: Cloudflare Access (оранжевое облако на `admin.callcord.ru`, вход по почте) **или** клиентский
   сертификат в браузере. Рекомендация — Access: не нужен сертификат на каждом устройстве, есть журнал входов у Cloudflare.
2. **Р-111: без Kubernetes** до условий §3.4 — подтвердить.
3. **Где `node.sh`/реестр**: на meet (вариант (а) §4.3, рекомендуется) — подтвердить; тогда SSH-ключи к B и cordcam должен
   получить meet (владелец/GPT кладёт), а A — ключ к meet.
4. **Токен GitHub** (чтение релизов и прогонов, запуск выпуска) — на A в `.local/fleet/`, или панель без GitHub.
5. **Стек `fleet`**: Java (рекомендация) или Go.
6. Имена: `admin.callcord.ru` для панели, `callcord.ru`/`rtc.`/`turn.callcord.ru` для стенда — подтвердить (Р-110′).
