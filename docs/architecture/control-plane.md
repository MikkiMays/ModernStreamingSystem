# Управление флотом без SSH: агент на каждой машине (R233)

Статус: **проект, принят к разработке** 12.11.2026. Заменяет в `admin-panel.md` §6.2 (туннели SSH к ядру), §6.3
(`SshExecutor`) и §6.4 (ключи root на A), а в `observability.md` — сбор метрик через туннели. Решения — Р-142…Р-146 (§9).

## 1. Что не так сейчас

Слова владельца: «сделано через подключения SSH, а это крайне небезопасно».

| Как сделано | Чем плохо |
| --- | --- |
| Служба `fleet` на A исполняет рычаги по SSH под `root` на машинах продукта; ключи `cord_fra`, `cord_msk`, `cord_fi` смонтированы в её контейнер | веб-служба, открытая в интернет, держит полные права на каждой машине продукта; A — машина разработки, на ней идут сборки, автотесты и сессии агентов |
| Постоянные туннели SSH с A: админ-API ядра продукта и экспортёры метрик каждой машины | каждый туннель — тот же ключ root; порты продукта проброшены на машину разработки |
| Ключ пульта к ядру продукта (`FLEET_KEY`) лежит на A | секрет продукта хранится вне продукта |
| Каталог операций проверяется на A, а исполняет удалённая оболочка | машина продукта верит всему, что пришло по SSH |
| Отозвать доступ можно только правкой `authorized_keys` на каждой машине | нет одной точки «отключить» |

## 2. Требования

1. С A на машины продукта **нет входящих подключений вовсе**: ни SSH, ни туннелей, ни проброшенных портов. Порт 22 для
   пульта не нужен; владельцу для аварийного входа он остаётся (его решение, §8).
2. Машина продукта **исполняет только операции каталога**, который вшит в неё саму. Свободной команды в протоколе нет.
3. Секреты продукта **не покидают машин продукта**; на A — только свои.
4. Задание подписано: машина исполняет его, только если подпись пульта верна. Подделать задание, перехватив
   соединение или шлюз, нельзя.
5. Отзыв машины и отзыв пульта — одним действием в одном месте.
6. Обрыв связи с A не влияет на продукт: встречи, входы, выкатка вручную работают как раньше.
7. Тот же канал несёт метрики и чтение админ-API — второй системы доступа рядом не появляется.

## 3. Схема

```
            машина продукта (meet, msk, hel, …)                         A (пульт)
  ┌─────────────────────────────────────────────────┐        ┌──────────────────────────────┐
  │ cord-agent (Rust, один файл, пользователь        │ HTTPS  │ edge → шлюз → fleet           │
  │ cord-agent, systemd)                             │ ─────► │   /api/agent/*                │
  │   ├─ опрос заданий (долгий запрос)               │ только │   очередь заданий (SQLite)    │
  │   ├─ исполнение операций каталога                │ исходя-│   подпись заданий Ed25519     │
  │   ├─ чтение петли: админ-API ядра, отчёты        │ щие    │   реестр машин и их ключей    │
  │   │   insight, реестр узлов                      │        │   приём метрик → VictoriaMetrics
  │   └─ сбор метрик с экспортёров петли             │        └──────────────────────────────┘
  │ ядро · insight · SFU · шлюз · экспортёры         │
  └─────────────────────────────────────────────────┘
```

Агент сам приходит на A по HTTPS (обычный сертификат имени, проверка как у браузера) и держит долгий запрос «есть ли
мне задание». Появилось — fleet отвечает сразу; нет — отвечает пусто через 25 с, агент спрашивает снова. Задержка рычага
— десятки миллисекунд, а на машине продукта не открыто ничего.

## 4. Доверие

| Что | Как устроено |
| --- | --- |
| Кто такой агент | при установке агент создаёт пару Ed25519; закрытый ключ не покидает машину (`/etc/cord-agent/agent.key`, 0600, владелец `cord-agent`). Открытый ключ заносится в реестр машин fleet |
| Запрос агента | заголовки `X-Agent-Id`, `X-Agent-Time`, `X-Agent-Nonce`, `X-Agent-Signature` = подпись строки `метод\nпуть\nвремя\nnonce\nSHA-256(тело)`; время — в пределах 60 с, nonce — один раз |
| Кто такой пульт | у fleet своя пара Ed25519 для заданий; открытый ключ вшивается в настройки агента при установке (`control.pub`) |
| Задание | `{id, machine, kind, args, issued_at, expires_at}` + подпись пульта; агент проверяет подпись, имя машины, срок (≤ 5 минут) и что `id` ещё не исполнялся |
| Отзыв машины | удалить её ключ в реестре — запросы отклоняются сразу |
| Отзыв пульта | заменить `control.pub` на машинах (операция `rotate-control`, подписанная старым ключом, или вручную) |
| Чего нет | сертификатов клиента, своего удостоверяющего центра, общих паролей, ключей SSH в контейнере службы |

Что получает тот, кто полностью захватил A: возможность ставить задания **из каталога** — выкатить подписанную версию,
дренировать узел, начать окно работ, читать админ-API. Оболочки на машинах продукта, базы, секретов продукта, ключей SFU
он не получает. Раньше получал root на каждой.

## 5. Каталог операций агента

Вшит в двоичный файл; аргументы — типы с проверкой, в `argv` подставляются без оболочки.

| Вид | Что делает на машине | Аргументы |
| --- | --- | --- |
| `status` | `docker compose ps`, коммит установки, аптайм, диск | — |
| `logs` | хвост журнала службы | служба из перечня, строк ≤ 500 |
| `active-meetings` | `backlog/bin/active-meetings.sh` | узел |
| `deploy` | `backlog/bin/deploy.sh` с дренажем | коммит (40 hex) или ветка из перечня, службы из перечня, `drain`, `force` |
| `rollback` | выкатка прежнего коммита | коммит из истории выкаток |
| `node.drain`, `node.undrain`, `node.check`, `node.deploy`, `node.update`, `node.add`, `node.remove` | `scripts/node-config.mjs`, `backlog/bin/node.sh` | id узла `[a-z][a-z0-9-]{1,15}`, поля формы |
| `publish-windows` | `backlog/bin/publish-windows.sh` | версия |
| `http` | запрос к петле: только `GET`/`POST`/`PUT`/`DELETE` на перечисленные приставки пути (`/api/v1/admin/`, `/api/v1/nodes`, `/internal/reports/`), ответ ≤ 2 МиБ; ключи (`FLEET_KEY`, ключ `insight`) агент подставляет сам из файла на машине | метод, путь, тело |
| `agent.update` | заменить себя подписанной сборкой | версия, SHA-256 |

Задания идут по одному на машину; `http` — отдельной очередью без ожидания рычагов. Вывод — построчно обратно во fleet,
отмена — сигналом процессу, срок — у каждой операции свой.

## 6. Метрики

Агент раз в 15 с читает экспортёры петли (перечень в настройках: `node`, `containers`, `core`, `sfu`, `gateway`,
`services`, `insight`) и шлёт текст метрик на `/api/agent/metrics`; fleet ставит метки `machine` и `kind` и кладёт в
VictoriaMetrics. Нет связи — агент держит последние 10 минут и дошлёт. Туннели и отдельный сборщик на машинах не нужны;
метки те же, что были, — панели и оповещения не меняются.

## 7. Изменения во fleet и пульте

- `AgentExecutor` вместо `SshExecutor`; `SshExecutor`, том `/keys`, `FLEET_SSH_MACHINES`, единицы `cord-fleet-tunnel@*`
  удаляются.
- `CoreLink` продукта ходит операцией `http`, а не на проброшенный порт; `FLEET_KEY` продукта с A убирается.
- Реестр машин — в базе fleet: имя, роль, открытый ключ агента, версия агента, когда был на связи. Экран «Машины»:
  добавить (выдаёт одноразовую строку установки), отозвать.
- Вход агентов — `https://<имя стенда>/api/agent/*` на шлюзе A; открыт без сертификата клиента (агенты подписывают
  запросы), предел частоты по адресу, тело ≤ 4 МиБ.
- Сухой прогон остаётся: задание с `dry_run` агент разбирает, проверяет и возвращает план, ничего не исполняя.

## 8. Установка и переход

1. Сборка `cord-agent` — статический файл (musl) в CI; на машину кладётся установщиком `infra/agent/install.sh`
   (создаёт пользователя `cord-agent` в группе `docker`, единицу systemd, ключ, настройки) и печатает открытый ключ.
2. Первая установка на каждую машину — последним использованием имеющихся ключей SSH (или руками владельца).
3. Проверка: все операции каталога через агента на стенде, затем на продукте; метрики идут через агента.
4. После проверки: туннели и `SshExecutor` выключаются, ключи убираются из контейнера fleet.
5. Ключи `/root/.ssh/cord_*` на A — аварийный вход владельца. Рекомендация: убрать их с A и держать у владельца, а на
   машинах продукта выключить вход по паролю (`OWNER-ACTIONS.md`).

## 9. Решения

- **Р-142. Управление — агент на машине, только исходящие соединения; SSH из службы пульта убирается.**
- **Р-143. Личность агента и подпись заданий — Ed25519, без сертификатов клиента и своего центра.** Отзыв — удалением
  ключа из реестра.
- **Р-144. Каталог операций вшит в агента; свободных команд в протоколе нет.**
- **Р-145. Секреты продукта для пульта (`FLEET_KEY`, ключ `insight`) живут только на машине продукта; пульт читает
  ядро операцией `http` агента.**
- **Р-146. Метрики несёт тот же агент; туннели сбора убираются.**

Почему не Cloudflare Tunnel и Access: Zero Trust в аккаунте не включён (нужны действия владельца с оплатой), а главное —
управление продуктом зависело бы от доступности Cloudflare из российских сетей, которую провайдеры режут с 2025 года
(Р-109). Замер 12.11.2026 с узлов: из дата-центров Москвы, Франкфурта и Хельсинки Cloudflare доступен, но для домашних и
мобильных сетей это не гарантия. Агент с прямым соединением от этого не зависит. Cloudflare остаётся там, где он силён и
безопасен для нас: DNS как код (`infra/dns/`), регистратор, перенаправления.

Почему не Kubernetes, Nomad, Teleport: Р-111 в силе — машин меньше десяти, встреча привязана к узлу, выкатка идёт через
дренаж; эти системы добавили бы слой, не убрав ни одного требования из §2.
