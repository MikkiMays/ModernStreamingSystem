# Развёртывание и эксплуатация

## VPS и DNS

**Для действующего VPS с Jarvis:** порт 443 уже занят. Используйте [инструкцию совместного размещения](frankfurt-installation.md), включая `--legacy-hosts`, TLS passthrough и перенос прежнего Caddy на loopback 8443. Команды обычного запуска ниже рассчитаны на отдельный сервер. [Исследование задержки и LAN](latency-and-network.md) учитывает последние сведения о CPU, полосе и освобождённом диске.

Целевой production-стенд — отдельный Linux VPS с Docker Engine и Compose v2. Начальный функциональный сервер: 4 vCPU, 8 ГБ RAM, публичный IPv4, 1 Гбит/с. Нагрузка 5 × 10 с двумя максимальными экранами требует измеренного канала минимум 2,5 Гбит/с и проверки CPU. Регион сначала Франкфурт; сравните RTT, потери и доступность до Франкфурта/Хельсинки из реальных сетей пользователей.

Для обычной установки пользуйтесь [пошаговой инструкцией](INSTALL.md) и `setup.sh` — он
выполняет всё описанное ниже сам. Этот документ нужен, когда шаги требуется разложить
вручную или разобраться в устройстве.

## Три режима

| Режим    | DNS-имена | TURN/TLS                       | Когда                                   |
| -------- | --------- | ------------------------------ | --------------------------------------- |
| `simple` | одно      | 5349, сертификат держит LiveKit | по умолчанию                            |
| `strict` | три       | 443 по SNI, TLS снимает edge    | в сети открыт только 443                |
| `ip`     | нет       | 5349, самоподписанный           | без домена                              |

Приложение и signaling разделяются по путям, поэтому отдельное имя для `rtc` нужно только
в `strict`. Отдельное имя для TURN нужно там же и ровно по одной причине: под одним именем
TURN/TLS и HTTPS неразличимы на 443, так как edge разводит трафик по SNI.

Когда TLS снимается на edge, LiveKit объявляет `turns:<domain>:443` без возможности задать
другой порт — это зашито в сервер. Поэтому в `simple` и `ip` сертификат держит сам LiveKit
и объявляет фактический 5349; `scripts/turn-cert.sh` синхронизирует файл с выпущенным Caddy.

Записи должны быть обычными DNS, без HTTP proxy/tunnel. DNS-провайдер сам по себе не задаёт маршрут медиапакетов. Не публикуйте AAAA, пока IPv6 и firewall не проверены. Имена `example.org` ниже — заменяемые примеры.

Актуальное размещение `meet.nikg.tech` и доказательства приёмки: [журнал развёртывания](deployment-meet-nikg-tech.md).

## Конфигурация

На VPS, в каталоге проекта, с Node.js 20+:

```bash
# simple — одно имя
node scripts/configure.mjs --domain=meet.example.org --ip=203.0.113.10

# strict — три имени, TURN поверх 443
node scripts/configure.mjs \
  --app=meet.example.org \
  --rtc=rtc.example.org \
  --turn=turn.example.org \
  --ip=203.0.113.10

# ip — без DNS, самоподписанный сертификат с IP в SAN
node scripts/configure.mjs --mode=ip --ip=203.0.113.10
```

Генератор создаёт `.env` и `infra/generated/{livekit.json,edge.json,redis.conf}` со случайными секретами. Он отказывается перезаписывать существующий `.env`, чтобы повторный запуск случайно не отозвал сессии. Эти файлы исключены из Git. IP в примере — документационный: используйте реальный адрес VPS. `livekit.json` — JSON, допустимый также для YAML-парсера SFU.

Java Properties могут переопределяться переменными окружения Spring, например `STREAM_MAX_PARTICIPANTS`, `STREAM_MAX_ROOMS`, `STREAM_RECOVERY_SECONDS`, `STREAM_FILE_MAX_BYTES`, `STREAM_ROOM_MAX_BYTES`, `STREAM_TOTAL_MAX_BYTES`, `STREAM_RETENTION_MESSAGES`. Значения валидируются при старте. `ADMISSION_OPEN=false` прекращает новые входы и создание комнат. Сервер сообщает клиенту recoverySeconds и лимиты через admission/capabilities. Пределы первой версии: 10 участников/2 экрана, 1440p60; SFU room limit должен согласовываться с настройками ядра.

Базовые лимиты находятся в `server/src/main/resources/application.yml`. При уменьшении файлового лимита также измените `tusd -max-size` в Compose; более строгая проверка core всё равно применяется до создания загрузки.

## Сеть и TLS

| Порт                    | Доступ                | Назначение                                 |
| ----------------------- | --------------------- | ------------------------------------------ |
| TCP 80                  | внешний               | ACME HTTP challenge                        |
| TCP 443                 | внешний               | HTTPS/WSS и TURN/TLS по SNI                |
| UDP 7882                | внешний               | WebRTC UDP mux                             |
| TCP 7881                | внешний               | резерв ICE/TCP                             |
| UDP 3478                | внешний               | TURN/UDP                                   |
| TCP 7880                | **только внутренний** | LiveKit HTTP/Twirp, обход gateway запрещён |
| TCP 5349                | зависит от режима     | `strict` — внутренний, после L4 TLS; `simple`/`ip` — внешний TURN/TLS |
| TCP 8080/8090/8091/1080 | loopback              | core, hooks, gateway, tusd                 |
| TCP 5432/6379           | loopback              | PostgreSQL/Redis                           |

Compose использует host networking, как VM-вариант LiveKit. Обычного `ports:` здесь нет; это осознанное требование Linux. `livekit` слушает адреса media node, поэтому firewall обязателен для его внутренних портов. До первого запуска:

```bash
# Укажите действующий SSH-порт VPS; сначала проверьте существующие правила.
sudo SSH_PORT=22 bash scripts/firewall.sh
docker compose config --quiet
docker compose build
docker compose up -d
```

Скрипт добавляет SSH-правило перед включением UFW и не сбрасывает старые правила. На уже настроенном VPS проверьте порядок: существующее более раннее разрешение для 7880 может отменить смысл позднего deny. Также настройте firewall панели хостинга. Публичные listeners проверяйте с другой машины.

L4 Caddy завершает TLS на 443 и направляет `turn.*` к 5349, HTTP-хосты — к внутреннему Caddy на 8091 с PROXY v2. Внешний HTTP advertising ограничен HTTP/1.1 для корректной передачи к gateway; WebSocket upgrades поддерживаются. Встроенный TURN получает `external_tls: true` и рекламирует внешний TLS 443. Сертификаты ACME сохраняются в отдельном томе. [Официальная VM-архитектура](https://docs.livekit.io/transport/self-hosting/vm/) и [порты](https://docs.livekit.io/transport/self-hosting/ports-firewall/).

Первый запуск получает сертификаты после готовности DNS. `gateway` не выдаёт сертификаты самостоятельно. Не направляйте signaling напрямую на 7880 и не размещайте API-ключ SFU в веб-сборке. Веб не содержит `VITE_*` секретов.

## Проверка размещения

```bash
docker compose ps
curl --fail http://127.0.0.1:8080/actuator/health
curl --fail https://meet.example.org/api/v1/capabilities
```

С внешней машины TCP 7880/5349/8080/8090/8091/1080/5432/6379 должны быть недоступны. Открыть встречу с двух настоящих сетей, проверить камеры и экран, затем в браузере принудительно включить relay-only для тестового клиента или заблокировать прямой UDP на тестовом устройстве. В диагностике должен появиться TURN; отдельно подтвердить TLS 443 по выбранной ICE-паре/захвату пакетов. Успешный HTTPS не подтверждает работоспособность TURN.

Внешний `/rtc` без медиатокена должен получить отказ. Исключённый участник со старым токеном также не должен войти. `/internal/*`, Twirp и Actuator публично не проксируются. tus GET запрещён: файлы выдаёт только `/api/v1/attachments/{id}/content` после проверки доступа.

## Наблюдаемость

Внутренний `/actuator/prometheus` содержит JVM, CPU, пул JDBC, HTTP timings; `/actuator/health` проверяет БД/Redis. Экспорт метрик не публикуется через gateway. На SFU и хосте измерять исходящий трафик, CPU, память, потери, открытые дескрипторы. `docker stats`, `pidstat`, `sar -n DEV` и браузерный WebRTC stats дополняют друг друга. В клиенте диагностическая панель считает FPS/битрейт/потери по разности соседних измерений.

Не включать access logs с query signaling, SQL parameter logging, request-body logging или дампы команд. Не хранить трассы Playwright с настоящими пользовательскими документами. CI использует синтетические имена/файлы; артефакты диагностических тестов живут 7 дней.

## Хранение и очистка

`uploads` — закрытый том, UID/GID 10001, права 0700. Он разделяется только между core/tusd; прямой file_server его не видит. Начальная настройка прав выполняется отдельным `volume-init`.

БД и upload-том этой версии содержат временные встречи. Исключите их целиком из автоматических снимков/бэкапов хостинга. Сохранять нужно исходники, зашифрованный комплект конфигурации и сертификаты. PostgreSQL WAL служит восстановлению процесса, не пользовательским архивом; внешнее архивирование WAL здесь не настроено. Логическое удаление не является криминалистически гарантированным стиранием SSD.

При отказе диска/tusd доступ по истёкшему сроку всё равно запрещён. Физическая очистка повторяется раз в минуту и не освобождает квоту до успешного удаления. Отказ Redis возвращает ошибку ограничения доступа, но уже установленный медиапоток не проходит через Redis ядра.

### Сколько места занимает Cord

Всё, что копится, ограничено сверху — не уборкой, а самим устройством. Отсюда потолок в
установившемся режиме, около **17 ГБ**:

| Что | Потолок | Чем задан |
| --- | --- | --- |
| Вложения во встречах | 10 ГиБ | `stream.total-max-bytes`; каждый файл живёт сутки (`stream.retention.messages`) |
| Музыка, принесённая в комнаты | 2 ГиБ | `MAX_TOTAL` в `services/cord_services/media.py`; трек живёт сутки |
| Образы рабочего набора | ~1,9 ГБ | gateway, core, services, SFU, БД, Redis, tusd, edge |
| Образы отката от `update.sh` | ~1,5 ГБ | один набор; прежние убирает само обновление |
| Выпуски клиента Windows | 0,8 ГБ | два каталога по 400 МБ, `--keep` у `publish-windows-release.py` |
| Журналы контейнеров | 0,8 ГБ | `max-size: 20m` × `max-file: 5` × восемь служб в `compose.yaml` |
| База, сертификаты, конфигурация | десятки МБ | встреча — это строка JSON, а не запись разговора |

Кэша сборки в таблице нет намеренно: он общий на всю машину и живёт сутки, а не принадлежит
Cord. Ни одна из строк не растёт сама по себе — растут они от действий: выпуск, обновление,
пересборка. Именно это и убирает суточный таймер.

### Встреча, в которую никто не возвращается

Судьбу завершённой встречи решает один вопрос: сохранил ли её себе хоть кто-то.

**Не сохранил никто — она уходит вместе с разговором.** Держать её не для кого: вернуться
можно только по ссылке из списка недавних, а список этот у того, кто уже ушёл.

**Сохранил хотя бы один — начинается отсчёт.** Неделя без единого входа, и встреча удаляется
целиком — снимок, события, расписки, — и пропадает из избранного **у всех** сразу, а не
только у того, кто её удалил: записи избранного стоят на `ON DELETE CASCADE`, и отдельного
«убрать у всех» здесь нет. Срок считается от **последнего входа человека**, а не от создания:
пока во встречу заходят, она остаётся, сколько бы месяцев ей ни было. Музыкальный бот в счёт
не идёт. Убрал последний из избранного — встреча снова несохранённая, со своим сроком.

Сроки задаются в `stream.retention` (`server/src/main/resources/application.yml`) словами, а
не секундами:

| Ключ | По умолчанию | Что это |
| --- | --- | --- |
| `saved-room` | `7 days` | сохранённая встреча без единого входа |
| `unsaved-room` | `immediately` | завершённая встреча, которую никто не сохранил |
| `closed-history` | `1 hour` | переписка и события после завершения |
| `messages` | `1 day` | сообщения, расписки, приглашения и вложения идущей встречи |

Понимаются `7 days`, `2 weeks`, `3 months`, `month`, `90m`, `never` и `immediately`; окончание
`s` необязательно, `m` — это **минуты**, а месяц — `mo` или `month` (месяц и год считаются как
30 и 365 дней). Непонятная строка не игнорируется: сервер не поднимется и скажет, что именно
не разобрал. Каждый ключ переопределяется переменной окружения — `SAVED_ROOM_RETENTION`,
`UNSAVED_ROOM_RETENTION`, `CLOSED_HISTORY_RETENTION`, `MESSAGE_RETENTION`.

`unsaved-room: immediately` — это ещё и окно на «я случайно вышел»: пока срок не истёк,
встреча открывается по прежней ссылке из списка недавних. Поставьте `1 hour`, если такое окно
нужнее освободившегося места.

Посмотреть, что близко к удалению, — запрос по закрытым комнатам (у идущей встречи отметка
отстаёт на время с последнего события в ней, и это нормально):

```bash
docker compose exec -T postgres psql -U streaming -d streaming -c "
  SELECT id, room_code, to_timestamp(last_seen_at/1000) AS last_seen,
         (SELECT count(*) FROM favorites f WHERE f.room_id = r.id) AS saved_by
  FROM rooms r
  WHERE (state::json->>'closedAt') IS NOT NULL
    AND last_seen_at < (extract(epoch from now()) - 6*86400) * 1000
  ORDER BY last_seen_at"
```

Привязка Telegram-чата к удалённой встрече не запирает чат: бот забывает её и заводит новую
комнату при следующем `/meet`.

### Суточная уборка

`infra/tidy.sh`, таймер `cord-tidy.timer`, ежедневно в 05:10. Ставит его `setup.sh`; на
сервере, поставленном раньше, — `update.sh` при первом же обновлении. Руками:

```bash
sudo bash infra/tidy.sh --dry-run   # показать, что уйдёт, ничего не трогая
sudo bash infra/tidy.sh             # убрать
sudo bash infra/tidy.sh --install   # поставить таймер
journalctl -u cord-tidy.service     # или /var/log/cord-tidy.log
```

Убираются выпуски клиента за пределами двух последних, образы отката кроме последнего
набора, разовые теги своих образов, копии `infra/generated.before-*` кроме двух, журналы
сборок в `.local` старше двух недель, безымянные слои и кэш сборки старше суток.

**Главное правило: уборка удаляет только то, что умеет вернуться сама.** База, том вложений,
`.env`, сертификаты, `infra/generated` и всё, что положил в `.local` человек, не трогаются ни
при каких условиях — включая кончающийся диск. Про такие каталоги уборка только рассказывает
в конце отчёта, с размерами.

**Порог свободного места.** `CORD_DISK_FLOOR_GB` (25 по умолчанию) — сколько у Cord должно
быть свободно всегда. Если после обычной уборки места меньше, включается вторая ступень:
уходит и набор отката, и весь кэш сборки, и все выпуски кроме отдаваемого. Всё это
возвращается сборкой или загрузкой с GitHub — ценой времени, а не данных. Если и после этого
места мало, служба завершается с ошибкой: это видно в `systemctl --failed` и означает, что
смотреть надо руками. Прочие ручки — `CORD_KEEP_RELEASES`, `CORD_KEEP_HOURS`,
`CORD_KEEP_BACKUPS`, `CORD_LOG_AGE_DAYS`.

Чего в уборке нет: тушения пожара. Журнал, растущий на 65 тысяч строк в секунду, успевает
убить машину между двумя ночными проходами — его держит потолок `max-size` в `compose.yaml`,
а не уборка. Проверка журналов в `tidy.sh` — тревожная лампочка на случай, если этот потолок
когда-нибудь снимут: она подрезает файл, сохраняет хвост в `/var/lib/cord-tidy/` и говорит об
этом вслух.

## Обновление и остановка

Обычное обновление — `./update.sh` из каталога проекта; что он делает и какие у него ключи,
описано в [INSTALL.md](INSTALL.md#обновление). Он перезапускает SFU, то есть обрывает идущие
звонки. Ниже — порядок, при котором не обрывается никто: вход закрывается заранее, и
обновление ждёт, пока комнаты опустеют сами.

1. Установить `ADMISSION_OPEN=false` в `.env` и применить только core: `docker compose up -d --no-deps core`. Существующее медиа остаётся в SFU, служебный WS восстановится после перезапуска ядра.
2. Проверить прекращение новых входов через capabilities. Дождаться завершения комнат. Число незакрытых комнат можно посмотреть без чтения содержимого:

```bash
docker compose exec -T postgres psql -U streaming -d streaming \
  -c "SELECT count(*) FROM rooms WHERE state::jsonb->>'closedAt' IS NULL;"
```

3. После нуля активных комнат обновить зафиксированные версии/digest и выполнить тесты. Собрать и перезапустить нужные сервисы.
4. Вернуть `ADMISSION_OPEN=true`, применить core и выполнить smoke-проверку. Шаг 3 при этом
   удобно делать тем же `./update.sh --yes`: комнат уже нет, и обрывать нечего.

`infra/generated/*` порождаются `scripts/configure.mjs` и в Git не хранятся, поэтому
изменения генератора до установленного сервера сами не доезжают. Их перевыпускает
`node scripts/configure.mjs --refresh`: он читает существующий `.env`, сохраняет все секреты
и переписывает только порождённые файлы. Аргументы установки — включая `--legacy-hosts`, без
которых соседний сайт на том же 443 потерял бы маршруты, — лежат в
`infra/generated/topology.json`. Установке, сделанной до появления этого файла, перевыпуск
откажет и назовёт, чего ему не хватает; создайте файл, повторив исходные аргументы установки.

Не выполнять `docker compose down -v` при обычном обновлении: эта команда удаляет тома. Не менять SFU API/session secrets посреди встречи. LiveKit имеет stop grace period 2 минуты, но это не замена остановке новых входов и ожиданию пользователей.

Один VPS — точка отказа. Перезапуск самого SFU завершает его WebRTC-соединения; бесшовное переживание аварии медиасервера этой версией не обещается. Windows loopback-стенд не проверяет firewall, L4/TURN TLS, Linux container permissions или производительность VPS.
