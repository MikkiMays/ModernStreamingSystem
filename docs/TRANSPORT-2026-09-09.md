# Маршруты Kiki / Клоди / Fleet и DNS-only — 9 сентября 2026

Утверждение «выключение Cloudflare ничего не ускорит» было слишком категоричным.
В этой системе несколько разных каналов, и у них разные маршруты. Для заданного
приоритета — минимальной задержки — DNS-only для nikg.tech и media.nikg.tech является
разумным вариантом, который нужно сравнить из сети пользователя. Прямой HTTPS уже
проверен с сохранением SNI и обычной проверкой сертификата; конфигурация готова.

| Канал | Проверенный маршрут | Что меняет DNS-only |
|---|---|---|
| Cord meet/rtc/turn | A 108.165.32.23, уже DNS-only | Ничего: проксирование уже выключено |
| WebRTC Kiki MediaMTX | ICE содержит 108.165.32.23, UDP/TCP 8189 | Сам медиапоток уже идёт напрямую |
| Публикация устройств | KIKI_MEDIA_PUBLISH_HOST=108.165.32.23, SRT 8890/UDP | Этот путь уже использует IP |
| WHEP/WHIP на media.nikg.tech | HTTPS через Cloudflare → Caddy → MediaMTX | Убирает посредника из установления соединения |
| Запасное HLS-видео /hls/* | HTTPS через Cloudflare → Caddy → MediaMTX:8888 | Меняет путь самих видеосегментов |
| Современная Клоди, DeskLink | Получает connect_ip от ядра; сначала прямой WebSocket, обычный путь после неудачи | Успешное прямое подключение уже обходит Cloudflare; меняется запасной путь |
| Современный Fleet Android | DeviceSocket → PreferredSocket с прямым DNS override и Proxy.NO_PROXY | Аналогично: прямой путь уже есть |
| Браузерные и прочие HTTP/WS-клиенты к nikg.tech | Обычное разрешение имени в адреса Cloudflare | Меняет HTTP и WebSocket, включая управление и первоначальную авторизацию |

Данные прочитаны из работающих контейнеров: kiki-core отдаёт
KIKI_CONNECT_IP=108.165.32.23; kiki-media получает MTX_WEBRTCADDITIONALHOSTS=108.165.32.23.
В Клоди прямой сокет сохраняет исходные SNI/Host и проверку сертификата, ожидает до 6 с,
затем пробует обычный адрес. У Fleet реализован такой же предпочтительный прямой путь.
Это подтверждает возможность, но не доказывает, что на каждом пользовательском
устройстве установлена версия с этим кодом и что прямой маршрут там успешно выбран.

## Измерение

Пять новых HTTPS-соединений на каждый маршрут, с сервера размещения приложений.
Для прямого маршрута использован `curl --resolve имя:443:108.165.32.23`, без `-k`.
Оба варианта вернули одинаковые ожидаемые коды: nikg.tech/api/v1/me — 401,
media.nikg.tech/ — 403. Сертификаты прошли проверку.

| Адрес | Через Cloudflare, медиана ответа | Напрямую, медиана ответа |
|---|---:|---:|
| nikg.tech/api/v1/me | 240 мс | 50 мс |
| media.nikg.tech/ | 252 мс | 41 мс |

Здесь прямой запрос возвращается на тот же сервер, поэтому результаты нельзя
переносить на устройство в России или считать измерением качества видео. Они
показывают цену этого конкретного промежуточного маршрута. Нужны также время входа,
RTT/loss/jitter установленного медиаканала и поведение без VPN/с VPN на устройстве.

На момент аудита nikg.tech и media.nikg.tech остаются proxied; meet/rtc/turn — DNS-only.
Доступа к изменению записей Cloudflare в этой сессии нет. Сам DNS не ускоряет кодирование,
не меняет FPS захвата и не превращает HTTP/WebSocket в UDP. Отказ от прокси может улучшить
HTTP/WS/HLS, но не обещает улучшения уже прямого WebRTC или прямого DeskLink/Fleet.

[WebSocket и возможные разрывы при обновлении сети Cloudflare](https://developers.cloudflare.com/network/websockets/).
