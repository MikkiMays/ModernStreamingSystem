# T09 — нагрузка, стоимость пользователя и архитектура под рост (02.11.2026)

Задача владельца 02.11.2026: большое нагрузочное тестирование на этом железе, где слабые места и что грузится
первым, сколько стоит пользователь и на сколько людей хватит сервера, 5–10 таких серверов, мощности на 1000 активных,
сравнение с Discord/Zoom, будущая архитектура (несколько ЦОД, балансировщик) — нарисовать на доске проекта.
Итог — `docs/load/2026-11-02-load-report.md`; схема — `docs/load/cord-scale-2026-11.cord-board`; скрипты —
`scripts/load/`; сырые итоги — `docs/load/2026-11-02/*.json`.

## Как шло

1. Чтение: правила, `CONTEXT.md`, архитектура, `capacity.md`, целевая архитектура 10.2026; два агента-разведчика
   (Opus) — модель стоимости по функциям (медиа, музыка, кинозал, доска, игры, события) и узкие места ядра и
   инфраструктуры для горизонтального роста, с ссылками на строки.
2. Канал: `iperf3` до `fra.speedtest.clouvider.net` — TCP 8×20 с: 845–848 Мбит/с отдачи, 811–813 приёма; UDP 1 200 Б
   300/600/900 Мбит/с — 0 % потерь (при 900 приёмник видел 853). `speedtest-cli` выбрал сервер в Канзасе (128 мс) —
   отброшен.
3. SFU: `lk load-test` 2.19.2 против `127.0.0.1:7880`, 16 прогонов (`scripts/load/batch1.sh`, `batch2.sh`); ядра и
   память SFU по cgroup. Перед каждым — `active-meetings.sh` («Живых встреч нет»).
4. Музыка: настоящий `cord-publisher` из образа служб, 1/8/16 ботов (`music_run.py`).
5. Ядро: теневое ядро (`core-shadow.sh`: тот же образ на :18080, своя PostgreSQL :15432 и Redis :16379, общий SFU,
   пределы антибота сняты) — чат/события, простой, волна входов, доска (`batch-core.sh`, `joinlt.mjs`).
6. Архитектура — Fable по брифу с замерами (ячейки Москва + Франкфурт, этапы 0–3, эфиры, сравнение, цены); правка
   чисел по замерам ядра и музыки — в отчёте.
7. Схема для доски: `scripts/load/board/render_board.py` из `diagram.json` → `.cord-board`; импорт проверен на
   стенде настоящей доской через Playwright (`web/.verify/board-import.spec.ts`, вне git): 251 элемент из 251.

## Главные числа

- Одно ядро SFU: 180–260 Мбит/с видео одним слоем, 80–100 Мбит/с simulcast-мелочи, ≈ 30 тыс. пакетов/с звука.
  Насыщение ВМ вместе с тестером — ≈ 250 Мбит/с (потери 11 % при 15×15, обвал при 20×20); у SFU счётчик отброшенного
  0, у ОС 44,5 тыс. `RcvbufErrors`. Оценка без тестера — 450–500 Мбит/с на эту ВМ.
- Память SFU — до 522 МиБ на 60 участниках тестера, после — 112 МиБ; при `mem_limit 1g` ≈ 150–200 участников.
- Бот музыки — 0,026 ядра и ≈ 23 МиБ.
- Ядро: 200 человек в комнатах по 20, сообщение раз в 10 с от каждого — 1,31 ядра Java + 0,79 PostgreSQL, событие
  p95 571 мс, 151 Мбит/с снимков; комнаты по 45 — p95 1,3 с. 1000 пустых комнат — ≈ 1 ядро на проходы. Входы — 60/с при
  ≈ 500 строках `rooms`, 30/с при ≈ 900.
- Доска: 20 курсоров 30 Гц в комнате — p95 1,6 с; две такие — p50 9 с (steal 25 %).
- Этот сервер — ≈ 70–90 человек в смеси; 1000 активных — ≈ 8 Гбит/с и ≈ 47 ядер сейчас, ≈ 4 Гбит/с после этапа 0.

## Оговорки

- Тестер и нагрузчики — на той же машине (трафик через `lo`), steal 4–25 %: переносимы ядра на мегабит/пакет и ЦП по
  cgroup, а задержки под нагрузкой завышены.
- Не мерены: TURN/TLS через edge, кинозал (нужны внешние площадки — посчитан по коду), реальные браузеры на клиенте.
  Остальное E18 (полный e2e, CI Windows, PoW на телефоне, живые проверки Windows) — не в этой задаче.
