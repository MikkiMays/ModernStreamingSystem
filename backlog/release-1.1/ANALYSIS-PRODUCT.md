## 1. Загруженность сервера — 4 палочки рядом с пингом

### 1.1 Что есть сейчас

- **Пинг серверов есть только в клиенте**, в родном окне «Серверы»: `desktop/src/shell/servers.js:52-68`. Это медиана
  трёх `HEAD /api/v1/ping` (`desktop/src/main/index.ts:1628-1644`), вызов `servers.ping` (`index.ts:1552-1556`). Тон
  числа: <80 мс — good, <200 мс — fair (`servers.js:67`). Запрос один раз на открытие окна, без обновления. Строка:
  флаг, имя, хост, пинг (`servers.html:16-27`).
- Окно «Серверы» **только по-русски**: «Серверы», «мс», подвал зашиты в `servers.html:30-34` и `servers.js:66`. Это
  нарушает X1 («во всех восьми языках»). В `shell-text.ts` для окна нет ни одной строки.
- **В вебе** «Сменить сервер» — меню каталога без пинга (`web/src/ui/ServerMenu.tsx:59-76`). Измерить пинг чужого
  сервера браузер не может: CSP `connect-src 'self' https://{$RTC_HOST} wss://{$RTC_HOST}` (`infra/Caddyfile:25`).
- **PING своего сервера** — тихий текст в подвале главной (`web/src/ui/home/HomeShell.tsx:178-179`) и строка в шапке
  встречи (`MeetingHeader.tsx:153-154`). Компонент — `web/src/ui/Ping.tsx:25-111`: опрос `/api/v1/ping` раз в 2 с.
  Показывается, только если включено «Показывать PING» (`ServerSection.tsx:82-84`, `preferences.ts:51,169`).
- **Метрики загрузки наружу нет.** Открытые маршруты ядра — `ping`, `capabilities`, `catalog` (`RequestGuard.java:30-36`).
  `capabilities` отдаёт только `admissionOpen`/`maintenance` (`ApiController.java:124-148`; на стенде:
  `"admissionOpen":true,"maintenance":false`). Счётчики есть только за паролем владельца:
  `GET /api/v1/activity/now` → `live, waiting, humans, connected, bots, screens` (`ActivityController.java:134-139`,
  `ActivityReport.java:54-94`).
- **Ёмкость:** `max-rooms: 8`, `max-participants: 20` (`application.yml:46-51`). Комната «занята», пока в ней есть человек
  на связи или ей меньше 30 с (`RoomState.java:268`). Отказ — `429 ROOM_LIMIT` (`RoomService.java:122-124, 448-451`).
  `docs/capacity.md` §3-4: одно ядро SFU — 150-200 Мбит/с пересылки, и **канал кончается раньше процессора**.
- Все службы в `network_mode: host` (`compose.yaml:21-341`), поэтому ядро видит `/proc/stat` и `/proc/net/dev`
  всего хоста. Это важно: на машине есть «steal» провайдера (`CONTEXT.md:110`, память `dev-machine-performance`).

### 1.2 Причины и пробелы

1. Загрузку нечем показать: ни у ядра, ни у SFU нет открытого, дешёвого и безопасного ответа «насколько я занят».
2. Пинг чужих серверов есть только в клиенте; в вебе его не будет без смены CSP. CSP — жёсткая граница, ослаблять нельзя.
3. Окно серверов не переведено и не обновляет числа.
4. DESIGN.md:322-324 советовал убрать PING совсем. Владелец теперь хочет и PING, и загрузку — настройка остаётся.

### 1.3 Предлагаемый дизайн

**Ядро — `GET /api/v1/load`** (открытый, как `ping`; `Cache-Control: public, max-age=5`, предел 120 в минуту на адрес):

```json
{ "level": 2, "state": "ok", "updatedAt": 1793451200000 }
```

- `level` — 1…4; `state` — `ok | busy | full | maintenance | closed`.
- Сырые числа (встреч, людей, CPU) наружу **не** уходят. Они остаются в `/activity/now` за паролем: количество идущих
  встреч — сведения об использовании, а человеку для выбора хватает ступени.
- Считает `LoadMeter` (`@Scheduled` раз в 5 с). Берётся максимум из четырёх долей:
  - встречи: `busy / maxRooms`;
  - люди: `connected / (maxRooms × 6)` — это «обычная встреча 5-6 человек» из комментария `application.yml:49-50`;
  - CPU хоста: занятость **вместе со steal** из дельты `/proc/stat`, сглаженная EWMA за 30 с;
  - канал: отдача из `/proc/net/dev` против `STREAM_UPLINK_MBPS` (по умолчанию 1000). Это эксплуатационная переменная
    `.env`, а не настройка в интерфейсе (X3).
- Пороги: доля < 0,25 → 1; < 0,50 → 2; < 0,75 → 3; иначе 4.
- Steal > 25 % поднимает ступень минимум до 3: это и есть «звонок дёргается».
- `busy ≥ maxRooms` → 4 и `full`; `Maintenance.on()` → `maintenance`; `!admissionOpen` → `closed`.
- Гистерезис: вверх — сразу; вниз — только после 30 с ниже порога на 0,05. Иначе палочки мигают.

**Ядро — `GET /api/v1/catalog/load`** — для веба, раз браузеру CSP не даёт ходить к соседям. Ядро читает полезную нагрузку
своего каталога (`CatalogController.java:47-58` читает тот же файл) и раз в 30 с опрашивает `/api/v1/load` соседей
сервер-сервер (таймаут 2 с). Ответ — `[{url, level, state, at}]`. Сосед без маршрута (старая версия, 404) → `unknown`.

**Набор — новый примитив `LoadBars`** (`web/src/ui/kit/LoadBars.tsx`, стиль в `kit.css`, показ в `/kit`):

- Четыре **одинаковые по высоте** палочки 3×12 px, зазор 2 px, радиус 1 px. Не «лесенка»: лесенка читается как сила
  сигнала («больше — лучше»), а рядом с пингом это прочтут наоборот. Одинаковые столбики с цветом читаются как шкала
  загрузки («больше — теснее»).
- Залито столько палочек, какова ступень. Цвет: 1-2 — `--success`, 3 — `--warning`, 4 — `--danger`. Пустые —
  `color-mix(in oklab, var(--muted) 35%, transparent)`. Только токены (DESIGN.md:12-17; цвета есть в `tokens.css:391-397`).
- Состояния:
  - нет данных — 4 пустые и «—»;
  - `full` — 4 красные и подпись «Мест нет»;
  - `maintenance` — 4 пустые и «Обновляется»;
  - `closed` — «Закрыт для новых встреч».
- Доступность: `role="img"`, `aria-label` — «Загрузка сервера: низкая» / «средняя» / «высокая» / «мест нет». `title` —
  то же плюс «обновлено N с назад». Отдельного Tooltip в наборе нет (`kit/index.ts`), Ping тоже живёт на `title`.
- Цифры не показываются.

**Где показывать:**

1. **Окно «Серверы» клиента** (`servers.js`) — главное место. Правый столбец: `[▮▮▯▯]  34 мс`, палочки слева от числа.
   Строка для диктора: «Германия, Франкфурт — пинг 34 мс, загрузка низкая». Пока окно открыто — обновлять раз в 10 с.

## 2. Полный экран на телефоне: «нижний» плохо, «внутренний» хорошо, Safari

### 2.1 Что есть сейчас

- Обе кнопки работают через один хук `useFullscreen` (`web/src/core/fullscreen.ts:45-103`). Если есть
  `document.fullscreenEnabled` — `requestFullscreen`; если нет — CSS-замена: `fallbackTarget` и `data-full`
  (`fullscreen.ts:90-100`).
- **«Нижняя»** (пульт: `CallDock.tsx:330-337`, на телефоне — пункт меню «ещё», `CallDock.tsx:250-252`) разворачивает
  **весь документ** (`MeetingView.tsx:86-87`). Замена на iPhone — `.meeting-fullscreen` / `.meeting-page[data-full]`
  (`stage.css:904-915`): прячет шапку, но сцена с маленьким кадром Twitch, пульт и панели остаются.
- **«Внутренняя»** (пульт плеера: `Chrome.tsx:333-341`) разворачивает **плеер** (`WatchTheater.tsx:110`). Замена —
  `.watch-theater[data-full]` с `position: fixed; inset: 0` (`theater.css:608-618`). Кадр на всё окно.
- На iPhone обе — замена, и **полоса адреса Safari остаётся** (так и написано в `fullscreen.ts:12-15`,
  `theater.css:601-606`). Отсюда слова владельца: «внутренний открывает на полный экран» (плеер на всё окно),
  «нижний — плохо» (развёрнута страница, а не кадр), «скрывались урлы» — не скрываются ни там, ни там.
- Родной плеер iPhone отвергнут из-за «теряем общую паузу и субтитры» (`fullscreen.ts:17-19`). Довод про паузу устарел:
  `onPlay`/`onPause` элемента уже становятся командами комнаты `watch.play`/`watch.pause` (`useRoomSync.ts:290-300`,
  `WatchTheater.tsx:280-288`). Пробел другой — перемотку (`seeked`) не слушает никто (grep по `theater/` пуст), и своя
  дорожка субтитров (`useCaptions`) в родном плеере не видна.
- `<video playsInline>` (`WatchTheater.tsx:269`). Есть PWA: `display: standalone` (`web/public/manifest.webmanifest:10`),
  `apple-mobile-web-app-capable` (`web/index.html:33-35`).
- Twitch — не рамка, а HLS через yt-dlp, прокси служб и hls.js (`services/.../providers/twitch.py:243-248`,
  `engines/hls.ts`). Значит, у нас есть настоящий `<video>`, и его можно развернуть по-родному.

### 2.2 Ограничения платформ (проверено)

- **iPhone Safari** (и любой браузер на iPhone): Fullscreen API для элементов **нет** — ни в iOS 18, ни, по заметкам
  Safari 27 beta, дальше. Есть только `HTMLVideoElement.webkitEnterFullscreen()`; события `webkitbeginfullscreen` /
  `webkitendfullscreen`, флаг `webkitSupportsFullscreen` — он истинен, когда пришли метаданные.
- **iPadOS Safari 16.4+**: `element.requestFullscreen()` без префикса, наш пульт сохраняется.
- **Android Chrome**: `requestFullscreen({navigationUI: 'hide'})` для элемента, а в полном экране —
  `screen.orientation.lock('landscape')`.
- **Electron**: `fullscreen` в списке разрешений (`desktop/src/main/windows/main.ts:27`).
- **Android Capacitor (WebView)**: полный экран элемента идёт через `WebChromeClient.onShowCustomView` (BridgeWebChromeClient
  Capacitor), `screen.orientation.lock` в WebView не работает — нужен плагин `@capacitor/screen-orientation`. Проверить
  на устройстве.

### 2.3 Предлагаемый дизайн

**Одно намерение — одна цель.** В `core/fullscreen.ts` появляется `fullscreenTarget()`: что разворачивать, решает
содержимое сцены, а не то, какую кнопку нажали.

- Сцена показывает фильм (`stageView === 'integration'`, `occupant.kind === 'cinema' && film`, `core/stage-view.ts:44-53`) →
  цель обеих кнопок — **плеер**. Одна подпись «Развернуть плеер» / «Свернуть», один значок, одно состояние.
- Открыт или закреплён чужой показ → цель — его `<video>`.
- Иначе — встреча, как сейчас.

**Способ — по платформе:**

1. **Есть Fullscreen API** (компьютер, Electron, Android Chrome, iPad): `requestFullscreen({navigationUI: 'hide'})` на
   контейнере плеера — наш пульт, общая пауза, свои субтитры. На телефоне Android после входа: кадр горизонтальный, а
   телефон держат вертикально → `screen.orientation.lock('landscape')`; на выходе — `unlock()`; ошибки молча глотаются.
2. **iPhone во вкладке Safari** (не `display-mode: standalone`): плеер → `video.webkitEnterFullscreen()`. Это настоящий
   полный экран: адресной строки нет, жесты iOS, AirPlay. Что для этого доделать:
   - `seeked` от пользователя (не эхо) при праве `watch.control` → `watch.seek`; без права → вернуть на секунду комнаты и
     показать «Перематывает тот, у кого пульт» (`watch-controls.ts`);
   - субтитры: текущую фразу дублировать в `TextTrack` (`video.addTextTrack('subtitles')` + `VTTCue`) — iOS рисует её
     сам;
   - `webkitendfullscreen` → вернуть наше состояние и пульт;
   - метаданных ещё нет (`webkitSupportsFullscreen === false`) → CSS-замена и тост «Ещё загружается — нажмите ещё раз».
3. **iPhone с экрана «Домой»** (standalone, адресной строки нет вовсе) → наша CSS-замена: она там и есть полный экран,
   и пульт остаётся наш.
4. **iPhone, встреча без видео на сцене** — CSS-замена плюс один раз на устройство подсказка (kit `Coachmark`):
   «Чтобы убрать адресную строку, добавьте Cord на экран „Домой“» — с переходом в `InstallHint`.

**Поведение в полном экране** — общее для любой платформы: пульт плеера уходит через 2,8 с (как сейчас), пульт встречи
скрыт, Esc / свайп назад сворачивают. Base UI-порталы уже направлены в плеер (`WatchTheater.tsx:100-108`), меню качества
видны.

### 3.1 Что есть сейчас

- Главное окно клиента — одна постоянная сессия `persist:cord` (`desktop/src/main/windows/main.ts:25, 152, 272`). Смена
  сервера — `chooseServer`: пишет `serverUrl`, готовит bootstrap и грузит origin другого сервера

  `meet.nikg.tech` свои:
  - `cord:preferences:v1` (`web/src/core/preferences.ts:137`): устройства, обработка звука, громкости, сочетания,

- Общее уже есть: оболочка в bootstrap присылает `theme`, `language` (один раз на origin), `showPing`,
  `notificationSounds` (`index.ts:1160-1170`), а preload сливает их в `localStorage` до первого скрипта страницы
  (`desktop/src/preload/server.ts:33-53`). Обратно идут только эти два флага (`web/src/core/preferences.ts:263-269`,
  проверка — `desktop/src/main/bridge/messages.ts:198-201`). То есть механизм «общее для всех серверов» **уже есть** —
  он просто охватывает два поля.
- Секрет профиля — свой на каждый сервер: `profile-<sha256(origin)>.dat`, зашифрован `safeStorage`
  (`desktop/src/main/settings.ts:150-163`). Это правильно: избранное принадлежит серверу.

- Android (Capacitor) — один сервер на сборку (`mobile/capacitor.config.json` → `server.url`), переключения нет.

### 3.2 Причины и пробелы

1. Настройки живут в хранилище origin → на каждом сервере свои.

3. **Подвох:** `MediaDeviceInfo.deviceId` в Chromium солится по origin. Сохранённый id камеры на другом сервере не
   совпадёт, поэтому устройства переносить по одному id нельзя.

### 5.3 Реклама Twitch («commercial break»)

- Откуда: Twitch вставляет рекламу **на своей стороне прямо в HLS** (SSAI). Зрителю без подписки или Turbo в поток

- **Можно ли убрать — нет, и это нормально.** Убрать значит подменить содержимое: делиться на всю комнату токеном

  вход не обходим». К тому же у прямого эфира во время перерыва нет контента, к которому можно перемотать.
- Что сделать честно:
  - У записей Twitch со вшитой рекламой уже работает «Пропустить рекламу»: `ad-breaks.ts:39` ловит
    `DATERANGE CLASS=…stitched-ad`.
  - У эфира — та же разметка, но не перемотка, а своя плашка поверх заставки: «Перерыв на рекламу у Twitch · ≈ 0:30» с
    обратным отсчётом из `DURATION`. Звук заставки — тише, звук встречи не трогаем. Сейчас `breaks` разбирается только
    у записи (`hls.ts`, комментарий «у записи, не у эфира»); для эфира нужен второй обратный вызов.

## 7. Токен Яндекс Музыки «отваливается» после перезахода (клиент)

### 7.1 Как устроено

- На устройстве токен лежит в `cord:preferences:v1.yandexMusicToken` (`preferences.ts:66, 188`; реестр
  `core/accounts.ts:47-58`). Попадает туда двумя путями:
  - «Настройки → Аккаунты»: QR без встречи — маршрут `services/yandex/device`, токен отдаётся устройству один раз
    (`services/cord_services/yandex.py:256-300`, Р-15 — `DECISIONS.md:1086`);
  - вставка вручную.
- Во встрече служба держит аккаунт в **сейфе комнаты**: `scope = "room:" + room_id` (`yandex.py:579-581`), запись —
  `connect()` (`yandex.py:128-142`), таблица `integrations` (`accounts.py:27-74`).

### 7.2 Почему отваливается (по убыванию вероятности)

1. **Вход по QR внутри встречи кладёт токен только в сейф комнаты.** «Подключить» без сохранённого токена открывает QR
   (`YandexIntegration.tsx:61-82`) → `/rooms/{id}/yandex/auth/{auth_id}` → `poll_auth` сохраняет токен в
   `room:<id>` и **не отдаёт его устройству** (`yandex.py:182-221`, в отличие от `_poll_device`, `:296-300`). Следующая
   встреча — новый `roomId`: несохранённая удаляется сразу, `application.yml:65` → «не подключено», снова QR. Это почти
   наверняка случай владельца.
2. **Сохранённый токен уходит в комнату только при включении музыки** (`useMusic.ts:183-191`) или по ручному
   «Подключить». Если музыку в комнате уже включил кто-то другой, или человек вернулся во встречу, автоматически ничего
   не происходит.
3. **Клиент:** `localStorage` свой у каждого origin. После смены сервера, или если клиент открылся на другом сервере
   каталога (по умолчанию в каталоге — `cordcam.ru`, `/api/v1/catalog`), токена «нет» (задача 3).
4. Не причина, а **утечка:** записи сейфа комнаты не удаляются никогда. `store.forget` чистит только музыку
   (`store.py:299-302`), `Vault.delete` зовётся только явным «Отключить» (`yandex.py:95-100`). Токены закончившихся
   встреч остаются в БД служб зашифрованными. Это противоречит смыслу Р-15 («на сервере не хранится»).

Нормально ли это — **нет**.

### 7.3 Исправление

1. **Службы:** у входа в комнате ответ `connected` несёт `token` — один раз и только тому участнику, что начал вход.
   Заявку (`claim`) привязать к `member.id`, а не только к области комнаты: сейчас её мог бы опросить любой участник
   той же комнаты, зная `auth_id` (`yandex.py:188`).
2. **Веб:** `YandexIntegration` сохраняет пришедший токен в настройки (`onStoredTokenChange`, `MusicWidget.tsx:126-127`).
3. **Веб — автоподключение:** у комнаты Яндекс не подключён, на устройстве токен есть, у человека есть `yandex.connect` →
   тихо отправить `connectToken`. Когда: при открытии музыки или вкладки Яндекса и при входе, если музыка уже включена.
   Повторы с отступом. На 401 в «Аккаунтах» — «Токен устарел, войдите заново».
4. **Службы — уборка:** при `forget(room_id)` и при закрытии комнаты — `vault.delete('yandex', 'room:'+id)`; плюс
   разовая уборка уже накопленного.
5. **Клиент:** общий зашифрованный секрет из задачи 3 (`safeStorage`, `userData` переживает обновления).

### 7.4 Файлы

- **Службы:** `cord_services/yandex.py` (`poll_auth`, привязка заявки к участнику), `store.py` / `app.py` (уборка
  сейфа), `tests/test_yandex.py`.

- **Клиент:** как в задаче 3.

- Автоподключение двух людей с разными аккаунтами: побеждает первый, второй не перезаписывает подключённый аккаунт

### 9.3 Архитектура

```
браузер A ─┐                   ядро (Java)                        ┌─ браузер B
Excalidraw │  wss /api/v1/board  BoardSocket ── BoardRoom(roomId)  │  Excalidraw
 onChange ─┼─► ops (надёжные) ──► LWW по элементу, seq++ ──────────┼─► updateScene(NEVER)
 pointer  ─┼─► presence/ink ───► мимо хранения, только рассылка ───┼─► курсоры, лазер, штрих «в процессе»
           │                     │ раз в 3 с и при уходе           │
           │                     ▼                                 │
           │                  Postgres room_boards (gzip-сцена)    │
           │                  файлы картинок — FILES_ROOT          │
```

**Почему ядро, а не новый Node-сервис или службы:**

- Ядро уже знает участников, пропуски, права, жизнь комнаты (закрыли — доска удаляется вместе с ней), сроки хранения,
  Postgres и Redis pub/sub для нескольких узлов (`RoomSocket.java:124, 141`).
- Слияние Excalidraw элементное: у элемента `version` и `versionNonce`. Ядру не нужен CRDT — достаточно «больший
  `version` побеждает, при равенстве — меньший `versionNonce`», как в `reconcileElements`. На Java это 30 строк.
- Новый рантайм (Hocuspocus/Node) на медленной машине — лишняя эксплуатация.
- Службы (Python) пересобираются долго (`CONTEXT.md:84`), а доска — не внешняя площадка.

**Отдельный обработчик WS `/api/v1/board`** (рядом с `/api/v1/events`, `EventConfig.java:23-24`): горячий путь не делит
замок и `flush` с событиями встречи.

Сообщения (JSON; сжатие `permessage-deflate`; одно сообщение ≤ 64 КиБ):

- клиент → ядро:
  - `auth {roomId, credential, since}`;
  - `ops {ops: [{el}]}` — вставка или замена элементов; удаление — `isDeleted: true`;
  - `presence {x, y, tool, laser?, selection?}` — ≤ 30 Гц, можно терять;
  - `ink {id, from, pts}` — дельта точек штриха «в процессе», ≤ 30 Гц, можно терять;
  - `ping`.
- ядро → клиент:
  - `scene {seq, elements, files}` — при входе и при потере `seq`;
  - `ops {seq, from, ops}`;
  - `presence {from, …}`, `ink {from, …}`;
  - `cleared {seq, by}`;
  - `error {code}`.

**Задержка «моментально у всех»:**

- Свой штрих рисуется локально сразу (0 мс): Excalidraw оптимистичен.
- Отправка — по кадру (`requestAnimationFrame`, ≤ 16 мс); `getCoalescedEvents()` даёт точность пера.
- Чужим штрих «в процессе» идёт **дельтой точек** (`ink`), а не всем элементом на каждое движение. Иначе трафик растёт
  квадратично: 500 точек × 30 Гц × 10 зрителей. Готовый элемент уходит одним `ops` при отпускании пера.
- Рассылка в ядре — без БД и без замка комнаты, < 2 мс.
- Курсоры — 30 Гц с интерполяцией сплайном на 60 к/с у получателя.
- Бюджет: локально 16 + сеть 10-40 мс (Европа) + 2 + кадр 16 ⇒ **p95 < 100 мс** у остальных. Метрика — в «Диагностику»
  (метка времени в `ops`, p50/p95).
- Обратное давление: у каждого сокета своя очередь. Эфемерное схлопывается до последнего значения на автора; надёжное
  не теряется. Переполнение → закрыть сокет, клиент возьмёт `scene` по `since`. Сейчас декоратор держит 5 с / 256 КиБ
  (`RoomSocket.java:30`).

**Хранение:**

- `room_boards(room_id PK, scene bytea gzip, seq, updated_at)` и `room_board_files(room_id, file_id, mime, size, path)`
  — следующая свободная `V__` миграция Flyway, применённые не трогать.
- Запись — раз в 3 с и когда уходит последний.
- Пределы: 10 000 элементов, сцена ≤ 8 МиБ, элемент ≤ 64 КиБ, картинок ≤ 32 по ≤ 4 МиБ.
- Типы файлов — `image/png|jpeg|webp|gif` с проверкой сигнатуры; запрещены типы элементов `embeddable`/`iframe`;
  ссылки элементов чистит Excalidraw (`@braintree/sanitize-url`).
- Картинки: `PUT/GET /api/v1/rooms/{id}/board/files/{fileId}` (пропуск участника).
- Доска удаляется с комнатой. У **сохранённой** встречи (избранное, 7 дней) доска остаётся — «вернётесь, доска на месте»,
  как в Телемосте.

**Жизнь и права:**

- `RoomState.board {openedBy, openedAt, drawers: 'all' | 'host'}` с `@JsonInclude(NON_NULL)`.
- Команды `board.open`, `board.close`, `board.settings`, `board.clear` — в `Contracts.COMMAND_TYPES`.
- Сцена: `stageBusy` соперничает с кинозалом и столами; `StageKind` получает `'board'`, выход к участникам — по R121.
- Матрица:

| Действие | Кто |
| --- | --- |
| `board.open` | класс интеграций |
| `board.draw` | участник; при `drawers = host` — только создатель |
| `board.clear`, `board.settings` | класс интеграций / создатель |
| `board.close` | открывший или создатель |

- Кому рисовать нельзя — `viewModeEnabled` и подпись «Смотрите: рисует ведущий». Ядро проверяет право при `auth` и
  при смене прав, отвергает `ops` без `board.draw`. Модерация мягкая, как везде.
